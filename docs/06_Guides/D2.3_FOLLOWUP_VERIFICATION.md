## 2. Repository Inventory Contract — `exists()`

| `exists(id)` | Check existence | bool |

This is listed under the **Repository Interface Contract** (Section 5.3) that "Every Repository MUST implement".

### Why was it not implemented in D2.3?

**It is inherited from `BaseRepository`.** No override was needed:

| File | Method | Override? |
|------|--------|-----------|
| `base.py` line 211 | `async def exists(self, id: UUID) -> bool:` | **Base implementation** (generic) |
| `evidence_repository.py` line 84 | `async def exists(...)` | **Overrides** (domain-specific logic) |
| `query.py` line 75 | `async def exists(*args, **kwargs) -> bool:` | **Overrides** (raises NotImplementedError for QueryRepositories) |
| `entity_repository.py` | `exists` | **Not overridden** — inherits from `BaseRepository` |
| `relationship_repository.py` | `exists` | **Not overridden** — inherits from `BaseRepository` |
| `entity_query_repository.py` | `exists` | **Not overridden** — inherits from `QueryRepository` (which blocks it) |

**BaseRepository.exists() implementation** (`base.py` line 211-220):
```python
async def exists(self, id: UUID) -> bool:
    """Check if an entity exists by primary key."""
    stmt = select(1).where(self._model_class.id == id)
    result = await self.session.execute(stmt)
    return result.scalar_one_or_default() is not None
```

**EntityQueryRepository** inherits from `QueryRepository`, which overrides `exists()` to raise `NotImplementedError` (read-only enforcement).

**Conclusion:** `exists()` is part of the approved contract and IS implemented — via inheritance from `BaseRepository`. The D2.3 implementation satisfies the contract. No gap.

## 4. UUIDv7 Infrastructure Assessment

### Current State

| Aspect | Fact |
|--------|------|
| Architecture spec | `08_Implementation_Architecture.md` §4.1: all PKs/FKs are UUIDv7 |
| Deployment note | `09_Database_Physical_Design.md` line 103: `gen_random_uuid()` must be replaced with `uuidv7()` at deploy time |
| Python implementation | `types.py` line 22: `#: Primary key type — UUIDv7 throughout the project.` |
| Actual code | Python stdlib `from uuid import UUID` — no UUIDv7 generator anywhere |
| Generation method | Caller-assigned (Service layer or test code creates UUID before calling `repo.create()`) |
| ORM type | `Mapped[Any]` — no version enforcement at DB or ORM level |
| Python version | 3.11.15 (project supports 3.10–3.12) |

### Impact Assessment

**Affected files if UUIDv7 is implemented:**

| Category | Files |
|----------|-------|
| Generator infrastructure | New file: `backend/src/backend/shared/domain/uuid_generator.py` (or similar) |
| ORM models | `memory_models.py` — add `server_default=text("uuidv7()")` or Python-side default |
| All Repositories | `base.py` `create()` method — may need to call generator if entity has no id |
| All Services | Service layer code that creates entities (currently assigns UUIDs manually or via test factories) |
| Tests | `test_entity_domain_repositories.py` and all other test files — remove `str(uuid4())` calls |
| DDL/Migrations | Alembic migrations — add `uuidv7` extension, update defaults |

**Expected implementation scope:**
1. Add `uuid7` Python library (e.g., `uuid7` package for Python 3.10+) or implement via `pg_uuidv7` PostgreSQL extension
2. Create a central UUID generator utility (`generate_uuid() -> UUID`)
3. Update `BaseRepository.create()` to auto-generate UUID if entity has no id
4. Update all ORM models to use the generator
5. Update all test fixtures and factories
6. Update DDL scripts and Alembic migrations

**Migration risk:** **Low to Medium**
- UUIDs are opaque identifiers — changing generation algorithm does not affect data integrity
- Existing data uses UUIDv4-compatible format; UUIDv7 is also 128-bit UUID
- No schema changes needed — only default value generation changes
- Risk is mainly in ensuring all entity creation paths use the new generator consistently

**Would completing it now reduce future refactoring?**

**Yes, significantly.** Every repository (all 12 planned) and every service layer entity creation currently relies on caller-provided UUIDs. Once UUIDv7 infrastructure is in place:
- No future repository implementation will need to handle UUID generation
- Test factories can use the generator automatically
- Data ordering benefits from UUIDv7's time-sortable property
- The architecture specification (`08_Implementation_Architecture.md`, `09_Database_Physical_Design.md`, `04_Schema_Archive_Reflect.md`) would be fully satisfied

**Recommendation:** Complete UUIDv7 infrastructure as a D2.1 subtask **before** proceeding to D2.4 (Reflection Domain). The effort is small (1 new file + updates to base.py and test factories) but eliminates a cross-cutting concern that affects all 12 repositories.
