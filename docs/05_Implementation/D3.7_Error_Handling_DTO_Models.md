## 1. Purpose

Establish the authoritative architecture for Service Contracts — DTO design, error modeling, exception mapping, validation strategy, cross-service DTO reuse, versioning, serialization boundaries, and verification strategy.

This document is a **frozen architecture contract**. No redesign. No simplification. No removal of existing principles.

## 2. DTO Design Principles

### 2.1 Core Principles

DTO is a Service Contract.

DTO is not a Domain Object.

DTO contains data only.

DTO contains:

- no business logic
- no workflow
- no persistence logic
- no validation logic
- no infrastructure references

All DTOs are immutable.

DTOs are independent from:

- Repository
- Engine
- Database
- ORM
- Transport Protocol

DTO lifecycle exists only at the Service Boundary.

DTO represents business semantics rather than implementation.

One Capability owns one primary Service Contract.

Serialization transparency.

### 2.2 DTO Characteristics

| Characteristic | Rule |
|----------------|------|
| Immutability | All DTO fields are final/readonly. No setters. |
| Data Only | DTOs contain serializable data fields only. |
| No Logic | No business rules, no workflows, no persistence. |
| No Infrastructure | No references to DB, ORM, HTTP, gRPC, file system. |
| No Validation | Validation rules belong to the Service or Entry layer, not DTOs. |
| Business Semantics | Field names express domain concepts, not technical structures. |
| Capability Ownership | Each Capability defines its own primary contract. |

### 2.3 DTO Independence

```
┌─────────────────────────────────────────────────────┐
│                  Entry Layer                         │
│  ┌───────────┐    ┌───────────┐    ┌───────────┐   │
│  │ HTTP DTO  │    │ MCP DTO   │    │ CLI DTO   │   │
│  └─────┬─────┘    └─────┬─────┘    └─────┬─────┘   │
│        │                │                │          │
│        └────────┬───────┴────────────────┘          │
│                 ▼                                    │
│          ┌─────────────┐                            │
│          │  Service    │                            │
│          │  Contract   │  ← DTO Boundary            │
│          └──────┬──────┘                            │
│                 │                                    │
│                 ▼                                    │
│          ┌─────────────┐                            │
│          │  Domain     │                            │
│          │  Model      │  ← Independent             │
│          └─────────────┘                            │
└─────────────────────────────────────────────────────┘
```

## 3. Service Contract Consistency

### 3.1 Uniform Contract Pattern

Every Service method follows a uniform pattern:

```
Command / Query
    ↓
Service
    ↓
Result
```

### 3.2 Contract Principles

| Principle | Description |
|-----------|-------------|
| **Explicit Input** | All inputs are explicit. No implicit state. |
| **Explicit Output** | All outputs are explicit. No hidden side effects. |
| **Capability-Oriented** | Contracts organized by business capability, not technical layer. |
| **Technology-Neutral** | Contracts do not depend on HTTP, gRPC, or any protocol. |
| **Stable Naming** | Naming follows consistent convention (see §3.3). |

### 3.3 Naming Conventions

| Type | Convention | Example |
|------|-----------|---------|
| Command DTO | `XXXCommand` | `CaptureMemoryCommand` |
| Query DTO | `XXXQuery` | `SearchMemoriesQuery` |
| Result DTO | `XXXResult` | `CaptureMemoryResult` |

### 3.4 Protocol Independence

- No protocol status codes in DTOs (HTTP 200, 404, etc.)
- No transport-specific fields (headers, cookies, session IDs)
- No framework-specific annotations in DTOs
- Protocol mapping occurs only in Entry Layer

### 3.5 Forward Compatibility

- DTOs support additive changes without breaking existing clients
- Unknown fields are ignored, not rejected
- Versioning is capability-oriented, not global

## 4. Command DTO

### 4.1 Definition

Command represents Business Intent.

### 4.2 Principles

| Principle | Rule |
|-----------|------|
| One Command = One Business Capability | Each Command addresses exactly one capability. |
| Immutability | Commands are immutable. |
| Complete Input | Command contains all business input required. |
| No Execution State | No internal state tracking. |
| No Business Result | No result fields. |
| No Infrastructure | No DB, file, or network references. |
| No Runtime Context | No request ID, correlation ID, or tenant context. |
| Idempotency-Neutral | Command itself does not enforce idempotency. |
| Execution-Independent | Command does not depend on sync/async execution. |

### 4.3 Command Structure

```
Command
├── Business Input Fields
└── (No metadata, no state, no result)
```

### 4.4 Examples

| Capability | Command |
|------------|---------|
| Capture | `CaptureMemoryCommand` |
| Import | `ImportMemoriesCommand` |
| Merge | `MergeEntitiesCommand` |
| Archive | `ArchiveMemoryCommand` |
| Reflect | `ReflectCommand` |
| Search | `SearchMemoriesCommand` |

### 5.1 Definition

Query represents Information Need.

### 5.2 Principles

| Principle | Rule |
|-----------|------|

| Immutability | Queries are immutable. |

## 6. Response / Result Model

### 6.1 Definition

Result represents Business Outcome.

### 6.2 Principles

| Principle | Rule |
|-----------|------|
| Immutability | Results are immutable. |
| Business Data Only | Contains business data, not infrastructure details. |
| Capability-Oriented | Result reflects the capability that produced it. |
| No Internal Objects | Never exposes internal domain objects. |
| No Null/Void | Always returns explicit Result DTO. |
| No Protocol Status | Never contains HTTP status codes. |
| Execution-Independent | Result does not depend on sync/async. |
| Forward-Compatible | Supports additive changes. |

### 6.3 Result Structure

```
Result
├── Business Data
├── Business Metadata (optional)
│   ├── Timestamp
│   ├── Version
│   └── Correlation ID
└── Domain Warnings (optional)
    ├── Warning Code
    ├── Warning Message
    └── Warning Context
```

### 6.4 Warnings vs Errors

| Aspect | Warning | Error |
|--------|---------|-------|
| Nature | Non-blocking observation | Blocking failure |
| Result Delivery | Result delivered with warning | No result delivered |
| Client Action | Informative | Requires handling |
| Example | "Partial result returned" | "Memory not found" |

## 7. Business Result vs Execution Result

### 7.1 Dual Result Principle

Two distinct result types exist:

| Type | Represents | Owned By |
|------|-----------|----------|
| **Business Result** | Domain Outcome | Domain Services (MemoryService, QueryService, EntityService, ReflectionService) |
| **Execution Result** | Runtime Outcome | TaskService, Infrastructure |

### 7.2 Key Distinctions

| Concept | Rule |
|---------|------|
| Business Success ≠ Execution Success | A task may execute successfully but produce a business error. |
| Execution Success ≠ Business Success | A business operation may succeed but the task execution may fail. |
| TaskService Returns Execution Result | TaskService returns `TaskInfo` (status, metadata), not business data. |
| Domain Services Return Business Result | Domain Services return business outcomes, not execution metadata. |
| Execution Info Does Not Pollute Business Contracts | Execution metadata stays in Execution Result, not Business Result. |
| Business Result Independent of Execution Strategy | Business Result does not change based on sync/async. |
| Execution Result May Be Deferred | Execution Result may be queried asynchronously. |

### 7.3 Terminology Definitions

| Term | Definition |
|------|-----------|
| **Business Result** | The domain outcome produced by a Service method. Represents the business value delivered. |
| **Execution Result** | The runtime outcome of executing a task or operation. Represents the technical success or failure. |
| **Operation Result** | Generic term for any result. Use only when the distinction between Business and Execution is irrelevant. |

## 8. Error Model

### 8.1 Error Taxonomy (Frozen)

The following error categories are frozen. No redesign.

| Category | Code Prefix | Description |
|----------|------------|-------------|
| **Validation Error** | `E001`–`E099` | Invalid input, constraint violation |
| **Conflict Error** | `E100`–`E199` | Resource state conflict (optimistic lock, duplicate) |
| **Capability Error** | `E200`–`E299` | Business operation cannot complete |
| **Persistence Error** | `E300`–`E399` | Database operation failure |
| **Background Error** | `E400`–`E499` | Background task execution failure |
| **Policy Error** | `E500`–`E599` | Business policy or permission violation |
| **Infrastructure Error** | `E600`–`E699` | Infrastructure layer fault (internal only) |

### 8.2 Error Principles

| Principle | Rule |
|-----------|------|
| Error is part of Service Contract | Errors are version-controlled architecture contracts. |
| Error represents failure to produce Business Result | Error is the negation of Business Result. |
| Transport-Independent | Error model is independent of HTTP, gRPC, etc. |
| Language-Independent | Error model is independent of Python, TypeScript, etc. |
| Stable Semantics | Error codes express stable business semantics. |
| Immutable | Error instances are immutable once created. |
| Business Context | Error may include business context for diagnosis. |
| No Recovery Logic | Error never contains recovery instructions. |
| Warning ≠ Error | Warnings are informational, not errors. |
| Capability-Oriented | Error codes are organized by Capability, not by layer. |

### 8.3 Error Structure

```
Error
├── Category (Validation, Conflict, Capability, Persistence, Background, Policy, Infrastructure)
├── Code (stable, version-controlled)
├── Message (human-readable, capability-oriented)
├── Context (optional, business context)
│   ├── workspace_id
│   ├── entity_id
│   └── capability_name
└── Cause (optional, root cause reference)
```

### 8.4 Error Mapping to HTTP

| Error Category | HTTP Status | Example |
|---------------|-------------|---------|
| Validation Error | 400 Bad Request | `E001: Invalid input` |
| Conflict Error | 409 Conflict | `E100: Optimistic lock failed` |
| Capability Error | 422 Unprocessable Entity | `E200: Evidence insufficient` |
| Persistence Error | 500 Internal Server Error | `E300: Database connection lost` |
| Background Error | 500 Internal Server Error | `E400: Task execution timeout` |
| Policy Error | 403 Forbidden | `E500: Insufficient permissions` |
| Infrastructure Error | 503 Service Unavailable | `E600: Network unreachable` |

> **Note**: Infrastructure Error never crosses the Service boundary. Entry Layer maps it to an appropriate visible error.

## 9. Exception Mapping

### 9.1 Principles

| Principle | Rule |
|-----------|------|
| Exceptions Never Cross Service Boundary | Service boundary converts exceptions to Errors. |
| Service Owns Exception Mapping | Each Service maps its own exceptions. |
| Semantic Mapping | Mapping is semantic, not implementation-based. |
| Taxonomy Alignment | Exception categories map to frozen Error categories (§8.1). |
| Infrastructure Hidden | Infrastructure details are hidden from callers. |
| Diagnostic Chains Preserved | Internal diagnostic chains preserved for logging only. |
| Deterministic Mapping | Same input always produces same mapping. |
| Protocol Mapping at Entry | Protocol-specific mapping occurs only in Entry Layer. |
| Unknown → Known | Unknown exceptions always map to a known Business Error. |

### 9.2 Mapping Chain

```
Repository Exception
    ↓ (RepositoryError → Persistence Error E-04)
Service Exception
    ↓ (Persistence Error → Capability Error E-03 / Conflict Error E-02)
Domain Exception
    ↓ (Domain Exception → Error Code + Message)
Entry Layer
    ↓ (Error → HTTP/MCP/CLI Response)
Protocol Response
```

### 9.3 Exception Categories

| Exception Type | Maps To | Example |
|---------------|---------|---------|
| `ValidationError` | E001–E099 | Missing required field |
| `DuplicateError` | E100–E199 | Unique constraint violated |
| `NotFoundError` | E200–E299 | Resource not found |
| `DomainIntegrityError` | E200–E299 | Business invariant violated |
| `ReadOnlyError` | E200–E299 | Write on read-only resource |
| `RepositoryError` | E300–E399 | Database operation failed |
| `TaskExecutionError` | E400–E499 | Background task failed |
| `PermissionError` | E500–E599 | Policy violation |
| `InfrastructureError` | E600–E699 | Internal fault |

## 10. Validation Strategy

### 10.1 Principles

| Principle | Rule |
|-----------|------|
| Service Owns Business Validation | Business validation belongs to Service, not Entry or Repository. |
| Validation Before Execution | Validation completes before business logic begins. |
| Validation Produces Error | Failed validation produces a Validation Error. |
| Deterministic | Same input always produces same validation result. |
| Side-Effect Free | Validation does not modify state. |
| Capability-Oriented | Validation rules are organized by Capability. |
| Transaction Boundary | Business validation completes before transaction begins. |
| Transport-Independent | Validation rules are independent of HTTP, gRPC, etc. |
| Execution-Independent | Validation rules are independent of sync/async. |
| Stable Contracts | Validation rules are stable architecture contracts. |

### 10.2 Layered Validation Model

```
┌──────────────────────────────────────────────────────┐
│  Layer 1: Protocol Validation                        │
│  - Syntax checks                                     │
│  - Format validation                                 │
│  - Type coercion                                     │
│  → Entry Layer                                       │
├──────────────────────────────────────────────────────┤
│  Layer 2: Business Validation                        │
│  - Required fields                                   │
│  - Business rules                                    │
│  - Capability constraints                            │
│  → Service Layer                                     │
├──────────────────────────────────────────────────────┤
│  Layer 3: Persistence Validation                     │
│  - Uniqueness constraints                            │
│  - Foreign key integrity                             │
│  - Domain invariants                                 │
│  → Repository Layer                                  │
├──────────────────────────────────────────────────────┤
│  Layer 4: Infrastructure Validation                  │
│  - Connection availability                           │
│  - Disk space                                        │
│  - Resource limits                                   │
│  → Infrastructure Layer                              │
└──────────────────────────────────────────────────────┘
```

### 10.3 Validation Ownership

| Layer | Validates | Produces |
|-------|-----------|----------|
| Protocol | Input format, syntax | Protocol error |
| Business | Business rules, constraints | Validation Error (E001–E099) |
| Persistence | Uniqueness, FK integrity | Persistence Error (E300–E399) |
| Infrastructure | Resource availability | Infrastructure Error (E600–E699) |

## 11. Cross-Service DTO Reuse

### 11.1 Principles

| Principle | Rule |
|-----------|------|
| Capability Owns Its DTO | Each Capability defines and owns its DTOs. |
| No Shared Business DTOs | Business DTOs are never shared across Services. |
| Shared Value Objects Only | Only stable Shared Value Objects may be shared. |
| Semantic Reuse | Reuse semantic components, not complete DTOs. |
| Composition Over Inheritance | Prefer composition over inheritance for DTO reuse. |
| Capability-Neutral Shared DTOs | Shared DTOs must remain capability-neutral. |
| Independent Shared Contract Layer | Shared contracts belong to an independent Shared Contract layer. |
| Independent Lifecycle | Shared contracts evolve independently from business contracts. |
| No Business DTOs as Shared Contracts | Business DTOs must never become shared contracts. |

### 11.2 Shared Value Objects

| Shared Object | Used By | Description |
|--------------|---------|-------------|
| `Identifier` | All Services | Stable identifier type |
| `Pagination` | QueryService, all read Services | Page size, cursor, offset |
| `TimeRange` | QueryService, ReflectionService | Start/end timestamps |
| `SortOption` | QueryService | Field and direction |
| `Locale` | All Services | Language/locale preference |
| `Language` | All Services | Source/target language |

### 11.3 DTO Reuse Strategy

```
Service A DTO          Service B DTO
├── shared_id          ├── shared_id
├── shared_name        ├── shared_name
├── unique_field_a     ├── unique_field_b
└── (composition)      └── (composition)
```

## 12. Versioning Strategy

### 12.1 Principles

| Principle | Rule |
|-----------|------|
| Stable Public Contracts | Service Contracts are stable public contracts. |
| Semantic Stability > Structural | Semantic stability is more important than structural stability. |
| Backward-Compatible Evolution | Prefer backward-compatible changes. |
| Capability-Independent Evolution | Capability contracts evolve independently. |
| Shared Contract Lifecycle | Shared contracts have independent lifecycle. |
| Stable Error Codes | Error Codes remain stable across versions. |
| Capability-Versioned | Versioning follows Business Capability evolution. |
| Deprecation Before Removal | Deprecated fields precede removal. |
| Infrastructure Isolation | Infrastructure changes never affect Service Contracts. |
| ADR for Breaking Changes | Breaking changes require Architecture Decision Record. |

### 12.2 Compatibility Matrix

| Change Type | Allowed | Requires ADR |
|-------------|---------|-------------|
| Add new optional field | ✅ | — |
| Add new capability method | ✅ | — |
| Rename error code | — | ✅ |
| Remove deprecated field | — | ✅ |
| Change field type | — | ✅ |
| Add required field | — | ✅ |
| Change capability semantics | — | ✅ |
| Modify error taxonomy | — | ✅ |

### 12.3 Deprecation Process

1. Mark field/method as deprecated in documentation
2. Add deprecation warning in implementation
3. Maintain deprecated element for ≥ 1 major version
4. Remove after deprecation period
5. Document removal in changelog

## 13. Serialization Boundary

### 13.1 Principles

| Principle | Rule |
|-----------|------|
| Serialization at Entry | Serialization belongs to Entry Layer, not Service. |
| DTO Is Boundary | DTO is the serialization boundary. |
| Protocol-Specific | Serialization is protocol-specific (JSON, MessagePack, etc.). |
| DTO Friendly | DTO must remain serialization-friendly (no circular refs). |
| No Semantic Change | Serialization never changes business semantics. |
| Lossless | Serialization should be lossless for business data. |
| No Domain Crossing | Domain Objects never cross serialization boundaries. |
| Persistence Independent | Serialization is independent of persistence format. |
| No Context Leak | Serialization never leaks execution context. |
| Entry Owns Errors | Serialization errors are handled by Entry Layer. |

### 13.2 Serialization Boundary Diagram

```
┌─────────────────────────────────────────────────────┐
│                   Entry Layer                        │
│                                                      │
│  ┌──────────┐    JSON/XML/MsgPack    ┌──────────┐  │
│  │ Protocol │ ◄────────────────────► │ Protocol │  │
│  │ Adapter  │                        │ Adapter  │  │
│  └────┬─────┘                        └────┬─────┘  │
│       │                                    │       │
│       └─────────── SERIALIZATION ─────────┘       │
│                    BOUNDARY                         │
│  ┌──────────────────────────────────────────────┐  │
│  │           Service Layer                      │  │
│  │                                              │  │
│  │  ┌──────────┐    ┌──────────┐               │  │
│  │  │  Command │    │  Result  │               │  │
│  │  │   DTO    │    │   DTO    │               │  │
│  │  └──────────┘    └──────────┘               │  │
│  │                                              │  │
│  │  ┌──────────┐    ┌──────────┐               │  │
│  │  │  Query   │    │  Error   │               │  │
│  │  │   DTO    │    │   Model  │               │  │
│  │  └──────────┘    └──────────┘               │  │
│  └──────────────────────────────────────────────┘  │
│                                                      │
│  ┌──────────────────────────────────────────────┐  │
│  │           Service Layer                       │  │
│  │                                              │  │
│  │  ┌──────────┐    ┌──────────┐               │  │
│  │  │ Domain   │    │ Domain   │               │  │
│  │  │  Model   │    │  Model   │               │  │
│  │  └──────────┘    └──────────┘               │  │
│  └──────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

### 13.3 Important Distinction

```
Protocol Version ≠ Service Contract Version
```

- **Protocol Version**: HTTP/1.1 vs HTTP/2, JSON vs MessagePack
- **Service Contract Version**: Capability semantics, DTO structure, Error taxonomy
- Protocol changes do not affect Service Contract Version
- Service Contract changes require ADR

## 14. Verification Strategy

### 14.1 Contract Verification Principles

| Principle | Rule |
|-----------|------|
| Verification Before Implementation | Contract verification precedes implementation. |
| Capability-Oriented | Verification is organized by Capability. |
| Complete Contracts | Every Capability must have a complete contract. |

### 14.2 Verification Checklist

#### DTO Consistency

- [ ] All Commands follow `XXXCommand` naming
- [ ] All Queries follow `XXXQuery` naming
- [ ] All Results follow `XXXResult` naming
- [ ] No DTO contains business logic
- [ ] No DTO contains infrastructure references
- [ ] All DTOs are immutable
- [ ] No ORM model leaks to DTO
- [ ] No Entry DTO propagates between Services

#### Layer Boundaries

- [ ] DTO boundary is enforced at Service interface
- [ ] Domain models do not cross Service boundary
- [ ] Serialization occurs only at Entry Layer
- [ ] Protocol-specific code does not enter Service Layer

#### Validation Ownership

- [ ] Business validation belongs to Service Layer
- [ ] Protocol validation belongs to Entry Layer
- [ ] Persistence validation belongs to Repository Layer
- [ ] No validation layer skips another layer

#### Error Mapping

- [ ] All exceptions mapped to Error taxonomy (§8.1)
- [ ] No exception crosses Service boundary
- [ ] Unknown exceptions map to known Business Errors
- [ ] Error codes are capability-oriented
- [ ] Infrastructure errors hidden from callers

#### Version Compatibility

- [ ] Breaking changes documented with ADR
- [ ] Deprecated elements maintained for ≥ 1 major version
- [ ] Error codes remain stable
- [ ] Shared contracts evolve independently

#### Serialization Boundaries

- [ ] No circular references in DTOs
- [ ] Serialization is lossless for business data
- [ ] Domain objects do not cross serialization boundary
- [ ] Execution context does not leak through serialization

#### Shared Contract Rules

- [ ] Shared objects are capability-neutral
- [ ] Business DTOs not used as shared contracts
- [ ] Shared objects use composition over inheritance
- [ ] Shared contract lifecycle is independent

#### Deterministic Behavior

- [ ] Same input produces same output
- [ ] Validation is deterministic
- [ ] Error mapping is deterministic
- [ ] Serialization is deterministic
