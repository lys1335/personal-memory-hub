## 1. Purpose

This document defines the **Service Test Suite Architecture** for the Personal Memory Hub.

It establishes:

- Service-level testing principles and responsibilities
- Contract-based black-box testing approach
- Test layer responsibilities within the Service scope
- Command / Query testing separation
- Result verification strategies
- Error contract testing
- Validation testing
- Exception mapping testing
- Boundary testing
- Determinism testing
- Compatibility testing
- Test taxonomy organization
- Verification strategy
- Documentation synchronization requirements

**Scope**: This document covers testing **within the Service layer** and the Service's interactions with Entry, Engine, Repository, and Infrastructure layers. It does NOT cover Entry-level protocol testing, Engine algorithm testing, or Repository SQL correctness — those are covered by their respective layer test specifications.

**引用**: 10_1 §2.1, 10_8 §3, D3.7 §13

## 2. Service Testing Principles

### 2.1 Core Principles

> **Service tests are contract-based black-box tests.** They verify that each Service produces the correct Business Result for given inputs, handles errors according to the frozen Error Taxonomy, and respects all architectural boundaries.

| # | Principle | Description |
|---|-----------|-------------|
| 1 | **Contract-Based Black-Box Testing** | Tests verify Service contracts (Command/Query/Result/Error), not internal implementation details. |
| 2 | **Testing Mirrors Architecture** | Test structure mirrors the five-layer architecture. Service tests focus on Service-layer responsibilities. |
| 3 | **Contract Stability** | Once a Service contract is frozen, tests become regression protection. Tests are not modified to pass broken implementations. |
| 4 | **Layer Isolation** | Each test isolates a single layer responsibility. Service tests verify Service behavior without depending on Entry protocol details or Repository SQL. |
| 5 | **Capability-Oriented Testing** | Tests are organized by Capability (Capture, Retrieve, Resolve, etc.), not by class or method. |
| 6 | **Deterministic Verification** | Service tests verify deterministic behavior: same input → same Business Result. Non-determinism (LLM calls, network) is mocked or deferred. |

### 2.2 Service Testing Scope

Service tests verify:

| Verify | Do Not Verify |
|--------|---------------|
| Command execution produces correct Business Result | Internal method call sequences |
| Error classification matches frozen Taxonomy (D3.7) | ORM query construction |
| Validation occurs before side effects | Protocol-specific serialization |
| Transaction boundaries (commit/rollback) | Engine algorithm internals |
| Service Independence (no cross-Service calls) | Repository SQL correctness |
| Command returns Identity/Result, Query returns State | Entry DTO transformation details |
| Workspace isolation enforcement | Infrastructure implementation details |

## 3. Test Layer Responsibilities (Service Focus)

Each test layer has a clearly defined scope. Service tests must not assert on behavior outside the Service layer.

### 3.1 Entry Test (Outside Service Scope)

Entry tests verify protocol-level concerns. Service tests do NOT cover:

| Entry Test Scope | Why Outside Service Scope |
|------------------|--------------------------|
| Protocol parsing (HTTP/MCP/CLI deserialization) | Belongs to Entry layer |
| DTO transformation (public DTO ↔ internal Command/Query) | Belongs to Entry layer |
| Authentication and authorization | Belongs to Entry layer |
| Response shaping (JSON/XML/CLI formatting) | Belongs to Entry layer |
| Error formatting (error code → HTTP status) | Belongs to Entry layer |

### 3.2 Service Test (Primary Focus)

Service tests verify:

| Service Test Scope | Description |
|--------------------|-------------|
| Use case orchestration | End-to-end workflow correctness within a Service |
| Transaction boundaries | Commit/rollback behavior, per-chunk vs whole-batch |
| Service independence | Verify no synchronous cross-Service calls |
| Domain event publishing | Events published after successful operations |
| Error model compliance | Result/Error usage per D3.7, exceptions never used for control flow |
| Recovery policy | ContinueOnError, StopOnFatal behavior |
| Capability routing | Correct Service method invoked for each capability |
| Command / Query separation | Commands return Identity/Result, Queries return State |
| Validation ownership | Business validation occurs before execution |
| Workspace isolation | Different workspaces produce isolated results |

### 3.3 Engine Test (Outside Service Scope)

Engine tests verify domain algorithm correctness. Service tests do NOT cover:

| Engine Test Scope | Why Outside Service Scope |
|-------------------|--------------------------|
| MemoryEngine domain capability correctness | Algorithm belongs to Engine |
| EntityEngine identity resolution invariants | Domain logic belongs to Engine |
| QueryEngine ranking and scoring | Algorithm belongs to Engine |
| ReflectionEngine memory pyramid evolution | Algorithm belongs to Engine |
| Stateless behavior verification | Engine property, not Service property |

### 3.4 Repository Test (Outside Service Scope)

Repository tests verify persistence correctness. Service tests do NOT cover:

| Repository Test Scope | Why Outside Service Scope |
|-----------------------|--------------------------|
| CRUD correctness (insert, read, update, delete) | Persistence belongs to Repository |
| Query correctness (complex queries, joins, aggregations) | SQL belongs to Repository |
| Transaction support (isolation levels, rollback) | Database belongs to Repository |
| Schema compliance | Physical design belongs to Repository |

### 3.5 Integration Test (Cross-Layer)

Integration tests verify flows that span multiple layers. Service tests within integration scope verify:

| Integration Test Scope | Service Responsibility |
|------------------------|----------------------|
| Entry → Service → Engine → Repository → Database | Service coordinates the flow correctly |
| External service integration (LLM API, vector store) | Service handles failures per recovery policy |
| End-to-end scenario (full user journey) | Service produces correct Business Result |
| Task Runtime integration | Service submits/tracks tasks correctly |
| Domain event flow | Service publishes events with correct payload |

### 3.6 End-to-End Test (Outside Service Scope)

E2E tests verify complete user journeys. Service tests do NOT cover:

| E2E Test Scope | Why Outside Service Scope |
|----------------|--------------------------|
| MVP scenario validation | Full system behavior |
| Multi-adapter verification | Entry layer concern |
| Performance baseline | System-level concern |
| Upgrade path validation | Migration concern |

## 4. Contract Testing

Service contracts are the primary testing target. All contracts are defined in D3.7 and must be verified by tests.

### 4.1 DTO Contract Testing

Verify that DTOs conform to D3.7 frozen principles:

| Test | Verification |
|------|-------------|
| **Command DTO immutability** | Command objects cannot be mutated after construction |
| **Query DTO purity** | Query objects never trigger side effects |
| **Result DTO explicitness** | Result objects always contain business data (never null) |
| **Capability-oriented naming** | XXXCommand, XXXQuery, XXXResult naming convention |
| **No protocol leakage** | DTOs contain no transport-specific fields |
| **Serialization compatibility** | DTOs serialize/deserialize correctly per protocol |

### 4.2 Result Contract Testing

Verify Result objects per D3.7 §5:

| Test | Verification |
|------|-------------|
| **Business Result contains business data** | Result has Business Data field populated |
| **Business Metadata present** | Optional metadata included when applicable |
| **Domain Warnings not Errors** | Warnings are separate from Errors |
| **No internal object exposure** | Result never contains Domain Model, ORM Model, or Engine object |
| **Never null or void** | Result always contains explicit XXXResult object |
| **Forward-compatible** | Result accepts new optional fields without breaking |

### 4.3 Error Contract Testing

Verify Error objects per D3.7 §7:

| Test | Verification |
|------|-------------|
| **Unified Error Contract** | All Services use the same Error hierarchy |
| **Error Classification** | Error maps to one of the 7 frozen categories |
| **Error Stability** | Error codes remain stable across versions |
| **Error Information Boundary** | Error contains business context, not infrastructure details |
| **Transport independence** | Error object is the same regardless of Entry protocol |
| **Language independence** | Error structure is consistent across implementations |

### 4.4 Serialization Contract Testing

Verify serialization per D3.7 §12:

| Test | Verification |
|------|-------------|
| **Lossless serialization** | DTO → JSON → DTO round-trip preserves all data |
| **Domain Objects don't cross boundary** | Serialized output never contains ORM/Engine objects |
| **Protocol-specific serialization** | JSON, MessagePack, etc. produce correct output |
| **Serialization errors handled by Entry** | Entry Layer catches and formats serialization errors |

### 4.5 Version Compatibility Testing

Verify versioning per D3.7 §11:

| Test | Verification |
|------|-------------|
| **Backward compatibility** | New version accepts old-format requests |
| **Stable versioning** | Error Codes remain stable across versions |
| **Compatibility matrix** | Allowed changes vs ADR-required changes verified |
| **Semantic compatibility** | Behavior unchanged for compatible contract versions |
| **Deprecation path** | Deprecated fields still work, new fields work alongside |

## 5. Command / Query Testing

Commands and Queries have fundamentally different verification requirements.

### 5.1 Command Verification

Commands change business state. Tests verify:

| Test | Verification |
|------|-------------|
| **Command produces expected Business Result** | Capture → MemoryResult with Identity |
| **Command has side effects** | Database write, event published |
| **Command is idempotent where specified** | Duplicate capture produces same Identity |
| **Command validates input before execution** | Validation Error before any side effect |
| **Command returns Identity, not full entity** | MemoryResult contains MemoryID, not full Memory |
| **Command respects workspace isolation** | Different workspaces produce different results |

### 5.2 Query Verification

Queries never change state. Tests verify:

| Test | Verification |
|------|-------------|
| **Query returns expected State** | Search → SearchResult with ranked memories |
| **Query is side-effect free** | No database writes, no events published |
| **Query is deterministic** | Same query on same data → same result |
| **Query supports pagination** | Continuation token works correctly |
| **Query returns State, not Identity** | Full domain objects/views returned |
| **Query respects workspace isolation** | Different workspaces produce different results |
| **Query projection is correct** | Summary, Detail, Graph, Timeline projections match spec |

### 5.3 Command / Query Separation Verification

| Test | Verification |
|------|-------------|
| **Command methods never return State** | Methods prefixed with `capture`, `import`, `merge` return Result/Identity |
| **Query methods never have side effects** | Methods prefixed with `retrieve`, `search`, `browse` are read-only |
| **No mixed Command/Query methods** | Single method cannot be both command and query |

## 6. Result Verification

### 6.1 Success Result Verification

| Test | Verification |
|------|-------------|
| **Business Result contains correct data** | MemoryResult has correct MemoryID, level, entityIDs |
| **Metadata is accurate** | Timestamps, counts, source references correct |
| **Domain Warnings are appropriate** | Only warnings relevant to the operation |

### 6.2 Failure Result Verification

| Test | Verification |
|------|-------------|
| **Error category is correct** | Validation Error for bad input, Conflict Error for duplicates |
| **Error code is stable** | E001-E099 for Validation, E100-E199 for Conflict, etc. |
| **Error message is business-oriented** | No infrastructure details in message |
| **Error context is sufficient** | Context includes relevant identifiers (MemoryID, EntityID) |
| **Error never contains recovery logic** | Error is data-only, recovery is in Service |

### 6.3 Result Invariants

Every Service Result MUST satisfy:

| Invariant | Description |
|-----------|-------------|
| **Immutability** | Result cannot be mutated after construction |
| **Explicitness** | Result always contains data (never null) |
| **Capability-orientation** | Result type matches the Capability that produced it |
| **No leakage** | Result never exposes internal objects (ORM, Engine, Domain) |

### 6.4 Metadata Verification

| Test | Verification |
|------|-------------|
| **Timestamp accuracy** | Created/updated timestamps match business time |
| **Count accuracy** | Batch operation counts match actual processed items |
| **Source attribution** | Result metadata correctly attributes data sources |
| **Workspace identification** | Result metadata includes correct workspace |

## 7. Error Contract Testing

### 7.1 Unified Error Contract

All Services MUST use the same Error hierarchy:

| Test | Verification |
|------|-------------|
| **Single Error hierarchy** | All Services import from `service.exceptions` |
| **Error categories match frozen taxonomy** | 7 categories: Validation, Conflict, Capability, Persistence, Background, Policy, Infrastructure |
| **Error codes are stable** | E001-E099 Validation, E100-E199 Conflict, E200-E299 Capability, E300-E399 Persistence, E400-E499 Background, E500-E599 Policy, E600-E699 Infrastructure |
| **Error is immutable** | Error fields cannot be modified after construction |
| **Error is transport-independent** | Same Error object regardless of Entry protocol |

### 7.2 Error Classification Testing

| Test | Verification |
|------|-------------|
| **Validation Error for bad input** | Missing required fields → Validation Error |
| **Conflict Error for duplicates** | Duplicate capture → Conflict Error |
| **Capability Error for unsupported operation** | Unsupported capability → Capability Error |
| **Persistence Error for DB failures** | Database unavailable → Persistence Error |
| **Background Error for unknown failures** | Unexpected exception → Background Error |
| **Policy Error for policy violations** | Workspace violation → Policy Error |
| **Infrastructure Error for infra problems** | Network timeout → Infrastructure Error |

### 7.3 Error Stability Testing

| Test | Verification |
|------|-------------|
| **Error codes don't change** | E001 is always Validation Error across versions |
| **Error structure doesn't change** | Error always has Category, Code, Message, Context, Cause |
| **Error mapping is deterministic** | Same exception → same Error category always |
| **Error taxonomy is frozen** | No new categories added without ADR |

### 7.4 Error Information Boundary Testing

| Test | Verification |
|------|-------------|
| **No infrastructure in Error** | Stack traces, SQL, connection strings never in Error |
| **Business context in Error** | Error includes MemoryID, EntityID, workspace when relevant |
| **Entry layer formats for protocol** | Entry layer adds HTTP status, MCP error code, CLI exit code |
| **Service layer produces business Error** | Service layer produces Error with business semantics |

## 9. Exception Mapping Testing

### 9.1 Validation Failure vs Exception Mapping

These are distinct concerns:

| Concern | Test Scope |
|---------|-----------|
| **Validation Failure** | Business rule violation → Validation Error (deterministic, documented) |
| **Exception Mapping** | Unexpected exception → Error category (semantic, infrastructure-hidden) |

### 9.2 Infrastructure Exception Mapping

| Test | Verification |
|------|-------------|
| **Database connection failure** | sqlite3.Error → Persistence Error |
| **Network timeout** | requests.Timeout → Infrastructure Error |
| **Disk full** | OSError (ENOSPC) → Infrastructure Error |
| **Vector store unavailable** | pgvector connection error → Infrastructure Error |

### 9.3 Domain Exception Mapping

| Test | Verification |
|------|-------------|
| **Duplicate entity** | IntegrityError → Conflict Error |
| **Invalid state transition** | ValueError → Capability Error |
| **Workspace conflict** | ConstraintViolation → Conflict Error |
| **Missing required resource** | NotFoundError → Capability Error |

### 9.4 Unknown Exception Mapping

| Test | Verification |
|------|-------------|
| **Unhandled exception** | Any uncaught Exception → Background Error |
| **Unknown error code** | Database error code not in mapping → Background Error |
| **Null exception** | None raised → no Error produced |
| **Exception chaining preserved** | Root cause preserved in Error.Cause for logging |

### 9.5 Mapping Stability Testing

| Test | Verification |
|------|-------------|
| **Mapping is deterministic** | Same exception → same Error category always |
| **Mapping doesn't leak infrastructure** | Error never contains exception type name |
| **Mapping is capability-oriented** | Same exception in different capabilities may map differently |
| **Mapping documented** | Exception mapping matrix is version-controlled |

## 10. Boundary Testing

### 10.1 Layer Boundary Testing

| Test | Verification |
|------|-------------|
| **No ORM leakage** | Service returns Domain Models, not ORM objects |
| **No Entry DTO propagation** | Entry DTOs don't leak between Services |
| **Three distinct layers** | Entry DTO ≠ Domain Model ≠ Repository ORM Model |
| **Single translation responsibility** | Each layer translates once into the next layer's exception model |

### 10.2 Serialization Boundary Testing

| Test | Verification |
|------|-------------|
| **DTO is serialization boundary** | Domain Objects never serialized directly |
| **Protocol-specific serialization** | JSON, MessagePack produce correct output |
| **Serialization errors handled by Entry** | Entry catches serialization errors |
| **Protocol Version ≠ Service Contract Version** | Protocol changes don't affect Service version |

### 10.3 Transaction Boundary Testing

| Test | Verification |
|------|-------------|
| **Per-Memory transaction** | Capture uses single-Memory transaction |
| **Batch transaction** | Import uses whole-batch transaction |
| **Rollback on failure** | Failed operation rolls back all changes |
| **No long-running transactions** | Transaction completes within single operation |

### 10.4 Capability Boundary Testing

| Test | Verification |
|------|-------------|
| **Capability owns its DTO** | No DTO shared between unrelated Capabilities |
| **Capability-oriented API** | Methods named by Capability, not by CRUD |
| **No cross-Service calls** | Service methods don't call other Services |
| **Service Independence** | Services collaborate through shared Engines, not direct calls |

### 10.5 Dependency Boundary Testing

| Test | Verification |
|------|-------------|
| **Service → Engine dependency** | Service depends on Engine interfaces, not implementations |
| **Service → Repository dependency** | Service depends on Repository interfaces, not implementations |
| **No Engine → Service dependency** | Engine is independent of Service |
| **No Repository → Service dependency** | Repository is independent of Service |

## 11. Determinism Testing

### 11.1 Contract Determinism

| Test | Verification |
|------|-------------|
| **Same Command → same Result** | Deterministic for non-LLM operations |
| **Same Query → same State** | Query results identical for same input data |
| **Same Error → same category** | Exception mapping is deterministic |
| **No time-dependent behavior** | Results don't depend on wall-clock time (except timestamps) |

### 11.2 Behavioral Determinism

| Test | Verification |
|------|-------------|
| **Idempotent commands** | Duplicate capture → same MemoryID |
| **Order-independent queries** | Same data queried in different orders → same result |
| **Workspace isolation** | Operations in different workspaces don't interfere |

### 11.3 Controlled Non-Determinism

| Test | Verification |
|------|-------------|
| **LLM calls mocked** | Non-deterministic LLM output replaced with fixed fixture |
| **Network calls mocked** | External API responses replaced with fixed fixture |
| **Random values seeded** | UUIDs, tokens use fixed seed in tests |
| **Non-determinism documented** | Where non-determinism exists, it is explicitly tested |

### 11.4 Repeatability

| Test | Verification |
|------|-------------|
| **Tests runnable in any order** | No test depends on execution order |
| **Tests runnable in parallel** | No shared mutable state between tests |
| **Tests clean up after themselves** | No leftover state between test runs |
| **Tests produce same result on rerun** | Deterministic tests always pass/fail consistently |

## 12. Compatibility Testing

### 12.1 Backward Compatibility

| Test | Verification |
|------|-------------|
| **Old clients work with new Service** | New Service accepts old-format Commands |
| **New clients work with old Service** | Old Service ignores new optional fields |
| **Deprecated fields still work** | Deprecated Command fields produce same Result |
| **Removed fields rejected gracefully** | Unknown fields → Validation Error, not crash |

### 12.2 Stable Versioning

| Test | Verification |
|------|-------------|
| **Error codes stable** | E001 is Validation Error in all versions |
| **Result structure stable** | XXXResult has same required fields across versions |
| **Command structure stable** | XXXCommand has same required fields across versions |
| **Version bump requires ADR** | Breaking changes documented via ADR |

### 12.3 Compatibility Matrix

| Change Type | Requires ADR | Test Verification |
|-------------|-------------|-------------------|
| Add optional field to Command | ❌ No | New field accepted, old field still works |
| Remove required field from Command | ✅ Yes | Old clients receive Validation Error |
| Change Error code mapping | ✅ Yes | Existing Error codes unchanged |
| Add new Error category | ✅ Yes | New category documented, old categories unchanged |
| Change Result structure | ✅ Yes | Backward-compatible evolution only |
| Infrastructure change (DB schema) | ❌ No | Service contract unchanged |

### 12.4 Semantic Compatibility

| Test | Verification |
|------|-------------|
| **Behavior unchanged for compatible versions** | Same input → same Business Result |
| **Performance doesn't degrade** | Operation completes within SLA |
| **Resource usage doesn't increase** | Memory, CPU within bounds |
| **External behavior consistent** | Same API contract across versions |

## 14. Verification Strategy

### 14.1 Architecture-Driven Verification

Service tests are derived from architecture documents:

| Document | Test Derivation |
|----------|----------------|
| **D3.1** | BaseService tests: workspace context, transaction helpers |
| **D3.2** | MemoryService tests: capture, import, merge, archive, lifecycle, restore |
| **D3.3** | QueryService tests: retrieve, search, browse, projection, analytics |
| **D3.4** | ReflectionService tests: reflect, consolidate, summarize, evaluate |
| **D3.5** | EntityService tests: identity, merge, alias, relationship, profile |
| **D3.6** | TaskService tests: submission, tracking, health, recovery |
| **D3.7** | Contract tests: DTO, Result, Error, Validation, Exception mapping |

### 14.2 Specification Before Test

| Step | Action |
|------|--------|
| 1 | Define test scope in capability design document |
| 2 | Create shared fixtures for the capability's data |
| 3 | Write deterministic tests before implementation |
| 4 | Add scenario data for positive and negative cases |
| 5 | Register new capability in golden dataset if applicable |
| 6 | Update regression suite if capability addresses known gap |

### 14.3 Positive / Negative Verification

| Test Type | Verification |
|-----------|-------------|
| **Positive** | Valid input → correct Business Result |
| **Negative** | Invalid input → correct Error classification |
| **Edge Case** | Boundary values → correct handling |
| **Stress** | High volume → correct batch behavior |

### 14.4 Traceability

| Test → Source | Description |
|---------------|-------------|
| Test → Design Document | Each test traces back to a specific section in 10_X |
| Test → Guideline | Each test verifies a specific Guideline (G-XXX) |
| Test → Capability | Each test belongs to a specific Capability |
| Test → Contract | Each test verifies a specific contract (DTO, Result, Error) |

### 14.5 Regression Protection

| Aspect | Verification |
|--------|-------------|
| **Growing suite** | Tests never removed, only added |
| **Contract protection** | Tests protect contracts, not implementation details |
| **Executable documentation** | Tests document what was learned from past bugs |
| **Golden dataset updates** | Updated only when design changes, not implementation changes |

### 14.6 Verification Coverage

| Area | Coverage Requirement |
|------|---------------------|
| **All Capabilities** | Every Capability has at least one positive and one negative test |
| **All Error Categories** | All 7 frozen Error categories are tested |
| **All Boundaries** | Layer, serialization, transaction, capability boundaries tested |
| **Determinism** | All deterministic behavior verified |
| **Compatibility** | Backward compatibility verified for all public contracts |
