## 2. Documentation Review Principles

### 2.1 Single Source of Truth

> **GitHub is the Single Source of Truth.** All documentation must reflect what is on GitHub, not what is in conversation history, AI memory, or informal notes.

| Rule | Description |
|------|-------------|
| **GitHub HEAD is authoritative** | When in doubt, GitHub wins |
| **Documents mirror GitHub** | Code must conform to documents, not vice versa |
| **No parallel truth** | Only one version of each fact exists — on GitHub |

### 2.2 Documentation Never Changes Architecture

> **Documentation updates are governance, not design.** They synchronize text, fix references, unify terminology, and ensure consistency. They never modify architecture.

| Allowed | Not Allowed |
|---------|-------------|
| Fix typos | Add new architecture principles |
| Update cross-references | Modify frozen documents |
| Unify terminology | Change Service Layer contracts |
| Synchronize status | Introduce new capabilities |
| Add governance documents | Alter Guideline content |
| Update README/INDEX/Roadmap | Change ADR decisions |

### 2.3 Synchronization Before Enhancement

> **Synchronize existing documentation before adding new content.** A consistent baseline is more valuable than an extensive but inconsistent one.

| Step | Action |
|------|--------|
| 1 | Verify cross-references resolve |
| 2 | Check terminology consistency |
| 3 | Synchronize README/INDEX/Roadmap |
| 4 | Update D3 status |
| 5 | Then add governance documents (glossary, style guide, registry) |

### 2.4 Traceability First

> **Every document must be traceable.** Readers must be able to follow a chain from any statement back to its source.

| Requirement | Description |
|-------------|-------------|
| **Section references** | Every §X.Y must resolve to a real section |
| **Guideline references** | Every G-NNN must exist and be correctly numbered |
| **ADR references** | Every ADR-NNN must exist and have correct status |
| **Related documents** | Every `**引用**` must point to an existing document |
| **Cross-links** | Every `→` link must resolve to a real file |

### 2.5 Consistency Over Completeness

> **A consistent incomplete document is better than an inconsistent complete one.** Prioritize fixing contradictions over adding new content.

| Priority | Action |
|----------|--------|
| 1 | Fix contradictions |
| 2 | Fix broken references |
| 3 | Fix terminology mismatches |
| 4 | Synchronize status fields |
| 5 | Add missing governance content |

### 2.6 Freeze Preservation

> **Frozen documents are protected.** Once a document is marked Frozen, no content changes are allowed without an ADR.

| Frozen Document | Freeze Date | Protection Level |
|-----------------|-------------|-----------------|
| D3.1–D3.8 | 2026-07-13 | Content locked. Only governance updates allowed. |

### 4.4 Architecture Glossary

> **Architecture Glossary** — Canonical Terminology Reference

| Term | Definition | Source |
|------|-----------|--------|
| **Capability** | A discrete, observable unit of Service behavior (e.g., Capture, Retrieve, Resolve) | D3.7 §1 |
| **Command** | An operation that changes business state; returns Identity or Result | D3.7 §3 |
| **Query** | An operation that reads business state; returns State | D3.7 §4 |
| **Business Result** | The domain outcome of a Service operation (e.g., MemoryResult) | D3.7 §5 |
| **Execution Result** | The runtime outcome of a Service operation (success/failure metadata) | D3.7 §6 |
| **Error Taxonomy** | The 7-category frozen error classification (Validation, Conflict, Capability, Persistence, Background, Policy, Infrastructure) | D3.7 §7 |
| **Service Independence** | Services never call other Services synchronously; they collaborate through shared Domain Engines | G-038 |
| **Command/Query Separation** | Commands return Identity/Result; Queries return State. No method is both. | D3.7 §2 |
| **Dual Result Principle** | Business Result and Execution Result are separate; one operation produces both | G-096 |
| **EntityID** | Stable identity anchor for Entities; never changes | ADR-008 |
| **Memory Pyramid** | Hierarchical memory structure (L0 Raw → L1 Summary → L2 Concept → L3 Insight) | D3.7 §5 |
| **L0 Memory** | Raw, immutable evidence-based memory; never altered | ADR-004 |
| **Workspace** | Isolated context boundary; operations in one workspace don't affect another | D3.1 |
| **Domain Engine** | Stateless domain algorithm component owned by a Capability | D3.1 |
| **Repository** | Persistence component; returns Domain Models, never ORM objects | D2 |
| **Entry Layer** | Protocol adaptation layer; owns DTO transformation and serialization | D3.7 §12 |
