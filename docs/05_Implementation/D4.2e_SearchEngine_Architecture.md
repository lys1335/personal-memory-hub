## 1. Purpose

### 1.1 Core Identity

SearchEngine is the **Discovery Domain semantic consistency owner**.

SearchEngine is a stateless domain engine responsible for Search intent interpretation, discovery planning, candidate discovery, candidate validation, candidate filtering, candidate ranking policy, and discovery domain consistency.

It owns:

- Search intent interpretation
- Discovery planning
- Candidate discovery
- Candidate validation
- Candidate filtering
- Candidate ranking policy
- Discovery domain consistency

SearchEngine is a **Domain Engine**, not a persistence wrapper. It does not call databases directly. It operates on Domain Models provided by Repository.

This document adheres to D4 principles:

- **One Domain Capability → One Engine**: SearchEngine owns Discovery domain only
- **Engine is a Stable Facade**: Public contract is stable, internal composition is private
- **Domain Result, Not Protocol Result**: Returns domain-level results
- **No Cross-Engine Calls**: SearchEngine never calls other Engines
- **Domain Consistency, Not Business Consistency**: SearchEngine ensures domain invariants, Service ensures business consistency
- **Algorithm Isolation**: Domain algorithms are isolated within SearchEngine

### 1.2 SearchEngine is NOT a Query Engine

SearchEngine is **NOT** a traditional Query Engine.

SearchEngine is the **Domain Consistency Owner for Discovery**.

Its responsibility is **Discovery Semantics**.

It does NOT perform:

- Workflow orchestration
- Repository coordination
- Data retrieval
- Persistence
- SQL generation
- Vector search
- Full-text search
- DTO assembly
- Context construction
- LLM invocation

SearchEngine **discovers Candidates**.

Repository **retrieves data**.

QueryService **assembles final business results**.

Discovery always precedes Retrieval.

### 1.3 Relationship with Other Engines

SearchEngine, EntityEngine, MemoryEngine, RelationshipEngine, and ReflectionEngine are sibling Domain Engines under the same architectural layer:

- **SearchEngine** owns Discovery semantics, candidate validation, and ranking policy
- **EntityEngine** owns Entity identity, canonical semantics, and evolution
- **MemoryEngine** owns Memory semantic consistency, evidence integrity, and lifecycle
- **RelationshipEngine** owns Relationship semantics, validity, and consistency
- **ReflectionEngine** owns Reflection semantics, candidate evaluation, and knowledge evolution

SearchEngine discovers Candidates within defined Scope. It never calls other Engines directly. Service coordinates between Engines.

### 1.4 Compatibility with ReflectionEngine

SearchEngine must remain fully compatible with the Open-Ended Knowledge Evolution Model defined in D4.2d.

SearchEngine must NOT depend on fixed layer names such as:

- Observation
- Pattern
- Belief

SearchEngine operates on **Knowledge Evolution semantics** rather than concrete knowledge hierarchy names.

Future systems may introduce additional knowledge levels without requiring architectural modification. SearchEngine must therefore remain independent from concrete hierarchy names.

## 2. Responsibilities

### 2.1 Search Intent Interpretation

SearchEngine interprets search intent for domain purposes:

- Extract semantic meaning from search request
- Determine discovery scope
- Identify candidate types required
- Establish ranking priorities

### 2.2 Discovery Planning

SearchEngine plans discovery strategy:

- Define discovery boundaries
- Select applicable discovery policies
- Establish candidate validation criteria
- Determine ranking approach

### 2.3 Candidate Discovery

SearchEngine discovers Candidates:

- Identify potential Candidates within scope
- Discover Candidates based on search intent
- Maintain domain neutrality in discovery
- Ensure Candidates satisfy domain constraints

### 2.4 Candidate Validation

SearchEngine validates Candidates:

- Verify Candidate existence
- Validate Candidate semantic integrity
- Check Candidate eligibility for ranking
- Ensure Candidate meets domain requirements

### 2.5 Candidate Filtering

SearchEngine filters Candidates:

- Apply discovery policies
- Remove invalid Candidates
- Enforce scope boundaries
- Maintain domain consistency

### 2.6 Candidate Ranking Policy

SearchEngine applies ranking policy:

- Evaluate Candidate relevance
- Apply ranking criteria
- Order Candidates by domain priority
- Produce ranked Candidate Set

### 2.7 Discovery Domain Consistency

SearchEngine ensures discovery domain consistency:

- Discovery never performs Retrieval
- Discovery never orchestrates Workflow
- Discovery never depends on Infrastructure
- Candidate validity guaranteed before exposure
- Discovery produces Candidate Sets, not final business results

### 2.8 Explicitly NOT Owned

SearchEngine does NOT own:

- **Workflow orchestration** — Service orchestrates multi-step workflows
- **Repository coordination** — Repository owns data access
- **Transaction management** — Service owns transaction boundaries
- **Data retrieval** — Repository handles actual data fetching
- **SQL generation** — Not a domain responsibility
- **Vector search** — Retrieval technology, not Discovery
- **Full-text search** — Retrieval technology, not Discovery
- **DTO assembly** — Service handles presentation
- **Context construction** — ContextBuilder handles context (D5)
- **LLM invocation** — Service manages AI provider communication
- **Entity identity** — EntityEngine owns Entity identity
- **Memory semantics** — MemoryEngine owns Memory consistency
- **Relationship semantics** — RelationshipEngine owns Relationship consistency
- **Reflection semantics** — ReflectionEngine owns Reflection consistency
- **Search/projection** — SearchEngine owns Discovery, ProjectionEngine owns view assembly
- **Cross-Engine coordination** — Service coordinates between Engines

## 3. Public Contract Principles

SearchEngine's public contract follows these principles:

### 3.1 Capability-Oriented

Methods are organized by domain capability, not by CRUD operations.

### 3.2 Stateless

SearchEngine has no mutable instance state. All state comes from Repository reads.

### 3.3 Deterministic

Given the same input Search Request, SearchEngine always produces the same Candidate Set.

### 3.4 Domain-Oriented

Returns domain-level results (DomainResult, DomainError), not protocol-specific types.

### 3.5 Side-Effect Free

SearchEngine does not directly modify Repository data. It returns domain commands that Service executes.

### 3.6 Explicit Result

Every method returns an explicit result indicating success, failure, or required action.

### 3.7 Repository Agnostic

SearchEngine operates on Domain Models, not database schemas.

### 3.8 Workflow Independent

SearchEngine makes domain decisions only. It does not orchestrate workflows.

### 3.9 Engine Independent

SearchEngine never calls other Engines. All Engine coordination happens at Service layer.

### 3.10 Discovery ≠ Retrieval

SearchEngine's public contract exposes **Discovery**, not **Retrieval**:

```
Search Request
↓
SearchEngine (Discovery)
↓
Candidate Set
↓
(Retrieval performed by Repository, outside SearchEngine)
```

SearchEngine discovers and ranks Candidates. It does not retrieve actual data.

## 4. Domain Rules

### 4.1 Search Intent Rules

#### 4.1.1 Explicit Search Intent

> Discovery requires explicit Search Intent.

- Every discovery operation must have a defined Search Intent
- Search Intent determines discovery scope and strategy
- Implicit or undefined intent results in rejection

#### 4.1.2 Intent Interpretation

> SearchIntent is interpreted semantically, not syntactically.

- Focus on domain meaning, not query syntax
- Intent drives policy selection
- Intent determines Candidate types required

### 4.2 Discovery Scope Rules

#### 4.2.1 Defined Scope

> Discovery operates within defined Scope.

- Scope limits discovery boundaries
- Scope prevents unbounded discovery
- Scope is part of Search Intent

#### 4.2.2 Scope Enforcement

> Scope is enforced at domain level.

- Candidates outside scope are excluded
- Scope violations result in empty results, not errors
- Scope respects domain isolation

### 4.3 Candidate Discovery Rules

#### 4.3.1 Candidate-Centric Discovery

> Discovery discovers Candidates rather than Domain Objects.

- Candidates are domain-semantically valid items
- Candidates are not raw database records
- Candidates are validated before ranking

#### 4.3.2 Domain Constraints

> Candidates must satisfy Domain Constraints.

- Domain Constraints defined by owning Engine
- Candidates failing constraints are filtered
- Constraint satisfaction is verified, not assumed

#### 4.3.3 Domain Neutrality

> Discovery remains Domain-neutral.

- SearchEngine does not assume specific domain types
- Discovery works with any valid Domain Model
- Domain-specific validation delegated to owning Engine

### 4.4 Discovery-Retrieval Separation Rules

#### 4.4.1 Discovery Precedes Retrieval

> Discovery always precedes Retrieval.

- SearchEngine produces Candidate Set first
- Repository retrieves actual data for Candidates
- Separation ensures domain purity

#### 4.4.2 No Retrieval in Discovery

> Discovery is independent from Retrieval Technology.

- SearchEngine does not know about SQL, vectors, or full-text
- SearchEngine does not care about persistence mechanism
- Retrieval technology is an implementation detail

#### 4.4.3 No Final Business Results

> Discovery produces Candidate Sets rather than final business results.

- Candidate Set is intermediate result
- Final business results assembled by Service
- SearchEngine does not produce DTOs or views

### 4.5 Knowledge Evolution Independence Rules

#### 4.5.1 Semantic Operations

> Discovery operates on Knowledge Evolution semantics.

- SearchEngine validates against Knowledge Evolution Model
- SearchEngine does not depend on fixed layer names
- Observation, Pattern, Belief are examples only

#### 4.5.2 Future Compatibility

> Future knowledge levels supported without architecture changes.

- New knowledge levels do not require SearchEngine modification
- Discovery adapts to configured Knowledge Evolution Model
- Semantic validation model-aware, not name-dependent

### 4.6 Ranking Policy Rules

#### 4.6.1 Relevance-Based Ranking

> Candidate ranking based on domain relevance.

- Relevance determined by Search Intent
- Ranking criteria configurable per domain
- Ranking is deterministic given same input

#### 4.6.2 Policy Isolation

> Ranking policy isolated from retrieval implementation.

- Policy defines what to rank by, not how
- Actual ranking execution independent of technology
- Policy changes do not affect retrieval mechanism

## 5. Domain Invariants

### 5.1 Discovery Never Performs Retrieval

> SearchEngine discovers Candidates. Repository retrieves data.

This is the fundamental boundary invariant. If violated, SearchEngine architecture is broken.

### 5.2 Discovery Never Orchestrates Workflow

> SearchEngine makes domain decisions only. Service orchestrates workflows.

SearchEngine does not coordinate multi-step operations.

### 5.3 Discovery Never Depends on Infrastructure

> SearchEngine operates on Domain Models, not infrastructure details.

SearchEngine is independent of database technology, search engine, or storage mechanism.

### 5.4 Candidate Validity Guaranteed

> Candidate validity is guaranteed before exposure.

No invalid Candidate is exposed through SearchEngine public contract.

### 5.5 Discovery Produces Candidate Sets

> Discovery never produces final business results.

SearchEngine output is always a Candidate Set, not a completed business object.

### 5.6 Discovery Domain-Driven

> Discovery is Domain-driven rather than Technology-driven.

Search decisions based on domain semantics, not query syntax or retrieval technology.

### 5.7 Knowledge Evolution Independence

> Discovery is independent of concrete Knowledge Evolution models.

SearchEngine validates against configured model, not fixed hierarchy names.

### 5.8 Equivalent Intent Equivalence

> Equivalent Search Intent produces equivalent Candidate Semantics.

Deterministic behavior guaranteed for same input.

### 5.9 Invariant Hierarchy

```
Domain Consistency
    │
    ├── Discovery ≠ Retrieval
    │       │
    │       ├── No Workflow Orchestration
    │       └── No Infrastructure Dependence
    │
    └── Candidate Validity
            │
            ├── Domain-Driven Discovery
            ├── Knowledge Evolution Independence
            └── Equivalent Intent Equivalence
```

All invariants are:

- **Universal**: Apply to all Discovery operations
- **Context Independent**: Not dependent on specific domain scenarios
- **Always Enforced**: No bypass mechanism exists

### 5.10 Invariant Extension Principle

> New invariants may be introduced in future versions only through architectural evolution while preserving backward compatibility, unless revised by ADR.

Any new invariant must:

- Not violate existing invariants
- Be justified by domain necessity
- Pass D4 principle consistency review
- Be documented with ADR if it changes existing behavior

## 6. Internal Composition

### 6.1 Architecture Overview

```
SearchEngine (Public Facade)
│
├── Intent Analyzer Capability       — Search intent interpretation
├── Discovery Planner Capability     — Discovery strategy planning
├── Candidate Validator Capability   — Candidate validation
├── Candidate Ranker Capability      — Ranking policy application
└── Candidate Assembler Capability   — Candidate Set assembly
```

SearchEngine is a **Facade**. Its internal composition is private. Service depends only on the public contract.

### 6.2 Capabilities

#### Intent Analyzer Capability

- Interprets Search Intent
- Extracts semantic meaning
- Determines discovery scope
- Identifies required Candidate types

#### Discovery Planner Capability

- Plans discovery strategy
- Selects applicable policies
- Establishes validation criteria
- Determines ranking approach

#### Candidate Validator Capability

- Validates Candidate existence
- Verifies semantic integrity
- Checks eligibility for ranking
- Ensures domain constraint satisfaction

#### Candidate Ranker Capability

- Evaluates Candidate relevance
- Applies ranking criteria
- Orders Candidates by priority
- Produces ranked output

#### Candidate Assembler Capability

- Assembles final Candidate Set
- Applies filtering rules
- Ensures domain consistency
- Prepares result for exposure

### 6.3 Composition Principles

| Principle | Description |
|-----------|-------------|
| **Composition Over Inheritance** | Internal capabilities use composition. Inheritance prohibited. |
| **Single Responsibility** | Each capability owns exactly one domain concern. |
| **Internal Collaboration Only** | Capabilities collaborate internally. Service never sees them. |
| **Replaceable Internal Capabilities** | Capabilities can be replaced without changing public contract. |
| **Stable Public Facade** | Public contract is the only dependency point for Service. |

## 7. Extension Points

### 7.1 Allowed Extensions

The following are architecturally open for extension:

| Extension Type | Category | Description |
|----------------|----------|-------------|
| **New Searchable Domain Objects** | B | Add new domain object types to discovery scope |
| **New Discovery Policies** | C | Add new discovery policies |
| **New Ranking Policies** | C | Add new ranking criteria |
| **New Knowledge Evolution Models** | C | Configure new Knowledge Evolution Models |
| **Retrieval Technology Replacement** | C | Replace underlying retrieval technology (outside SearchEngine) |
| **Search Algorithm Evolution** | C | Evolve search algorithms within domain rules |
| **Discovery Strategy Evolution** | C | Improve discovery strategies |

### 7.2 Architecturally Closed

The following are closed and require ADR to change:

| Closed Aspect | Reason |
|---------------|--------|
| **Domain Scope** | Discovery domain is fixed by architecture |
| **Layer Responsibility** | Engine layer cannot own workflow or persistence |
| **Engine Dependency Model** | Engine calls Repository only, never other Engines |
| **Public Contract Stability** | Contract changes require ADR |
| **Domain Invariants** | Existing invariants cannot be weakened |
| **Discovery ≠ Retrieval Boundary** | Fundamental separation cannot be crossed |

### 7.3 Extension Principles

| Principle | Description |
|-----------|-------------|
| **Open for Domain Evolution** | New domain rules and capabilities can be added |
| **Closed for Architectural Responsibility** | Layer boundaries cannot be crossed |
| **Stable Public Contract** | Extensions must not break existing contract |
| **No New Engine Without Independent Capability** | No new Engine unless a completely independent Domain Capability emerges |
