## 1. Purpose

### 1.1 Core Identity

RelationshipEngine is the **Relationship Domain semantic consistency owner**.

RelationshipEngine is a stateless domain engine responsible for Relationship semantic validation, domain rule enforcement, invariant protection, lifecycle consistency, semantic interpretation, and normalization.

It owns:

- Relationship semantic validation
- Relationship domain rule enforcement
- Relationship invariant protection
- Relationship lifecycle consistency
- Relationship semantic interpretation
- Relationship normalization

RelationshipEngine is a **Domain Engine**, not a persistence wrapper. It does not call databases directly. It operates on Domain Models provided by Repository.

This document adheres to D4 principles:

- **One Domain Capability → One Engine**: RelationshipEngine owns Relationship domain only
- **Engine is a Stable Facade**: Public contract is stable, internal composition is private
- **Domain Result, Not Protocol Result**: Returns domain-level results
- **No Cross-Engine Calls**: RelationshipEngine never calls other Engines
- **Domain Consistency, Not Business Consistency**: RelationshipEngine ensures domain invariants, Service ensures business consistency
- **Algorithm Isolation**: Domain algorithms are isolated within RelationshipEngine

### 1.2 Relationship with Other Engines

RelationshipEngine, EntityEngine, and MemoryEngine are sibling Domain Engines under the same architectural layer:

- **RelationshipEngine** owns Relationship semantics, validity, and consistency
- **EntityEngine** owns Entity identity, canonical semantics, and evolution
- **MemoryEngine** owns Memory semantic consistency, evidence integrity, and lifecycle

Relationships connect Entities. RelationshipEngine validates that every relationship satisfies domain rules. EntityEngine manages the Entity identities at relationship endpoints. MemoryEngine manages Memories that may reference Entities and Relationships.

Relationships belong to the current Identity Graph. Relationships may evolve together with Entity. Memory references never evolve.

## 2. Responsibilities

### 2.1 Relationship Semantic Validation

RelationshipEngine validates that each Relationship satisfies domain invariants:

- Endpoint compatibility (both endpoints are valid Entities)
- Relationship type validity (type exists in domain registry)
- Cardinality constraints respected
- Direction rules enforced

### 2.2 Relationship Domain Rule Enforcement

RelationshipEngine enforces domain rules:

- Relationship type rules (valid types and their constraints)
- Endpoint compatibility rules (allowed endpoint combinations)
- Direction rules (directed vs undirected relationships)
- Cardinality rules (one-to-one, one-to-many, many-to-many)

### 2.3 Relationship Invariant Protection

RelationshipEngine protects domain invariants:

- Valid Endpoint Invariant
- Relationship Type Invariant
- Semantic Integrity Invariant
- Structural Integrity Invariant
- Canonical Representation Invariant
- Domain Consistency Invariant

### 2.4 Relationship Lifecycle Consistency

RelationshipEngine manages domain-level relationship lifecycle:

- Creation validation (new relationships must satisfy all invariants)
- Evolution rules (relationship changes follow domain rules)
- Deactivation (relationships may be deactivated, not deleted)
- Historical preservation (relationship history maintained through evidence)

### 2.5 Relationship Semantic Interpretation

RelationshipEngine interprets relationship semantics:

- Relationship type meaning within domain context
- Semantic implications of relationship changes
- Interpretation of relationship networks
- Context-aware semantic analysis

### 2.6 Relationship Normalization

RelationshipEngine normalizes relationship representations:

- Canonical representation of equivalent relationships
- Deduplication of semantically identical relationships
- Normalization of relationship direction and labeling
- Consistent representation across domain operations

### 2.7 Explicitly NOT Owned

RelationshipEngine does NOT own:

- **Repository coordination** — Repository owns data access
- **Transaction** — Service owns transaction boundaries
- **Workflow** — Service orchestrates multi-step workflows
- **Entity creation** — EntityEngine owns Entity identity
- **Memory creation** — MemoryEngine owns Memory semantics
- **Graph traversal** — Not a domain responsibility of RelationshipEngine
- **Search** — SearchEngine owns retrieval algorithms
- **Projection** — ProjectionEngine owns view assembly
- **Reflection** — ReflectionEngine owns reflection algorithms
- **Cross-Engine coordination** — Service coordinates between Engines

## 3. Public Contract Principles

RelationshipEngine's public contract follows these principles:

### 3.1 Capability-Oriented

Methods are organized by domain capability, not by CRUD operations.

### 3.2 Stateless

RelationshipEngine has no mutable instance state. All state comes from Repository reads.

### 3.3 Deterministic

Given the same input Relationship and context, RelationshipEngine always produces the same Domain Result.

### 3.4 Domain-Oriented

Returns domain-level results (DomainResult, DomainError), not protocol-specific types.

### 3.5 Side-Effect Free

RelationshipEngine does not directly modify Repository data. It returns domain commands that Service executes.

### 3.6 Explicit Result

Every method returns an explicit result indicating success, failure, or required action.

### 3.7 Repository Agnostic

RelationshipEngine operates on Domain Models, not database schemas.

### 3.8 Workflow Independent

RelationshipEngine makes domain decisions only. It does not orchestrate workflows.

### 3.9 Engine Independent

RelationshipEngine never calls other Engines. All Engine coordination happens at Service layer.

## 4. Domain Rules

### 4.1 Relationship Type Rules

#### 4.1.1 Type Validity

> Every Relationship must have a valid Relationship Type from the domain registry.

- Types are domain-defined, not protocol-defined
- New types require domain justification
- Type changes follow evolution rules

#### 4.1.2 Type Constraints

> Each Relationship Type has specific constraints.

- Endpoint compatibility constraints
- Cardinality constraints
- Direction constraints
- Semantic constraints

### 4.2 Endpoint Compatibility Rules

#### 4.2.1 Valid Endpoints

> Both endpoints of a Relationship must be valid Entities.

- Endpoints are verified against EntityEngine capabilities (through Service)
- Invalid endpoints prevent relationship creation
- Endpoint validity is checked at domain level

#### 4.2.2 Endpoint Uniqueness

> Each relationship instance connects specific endpoint pair.

- Duplicate relationships between same endpoints are normalized
- Multiple relationship types between same endpoints are allowed
- Direction matters for directed relationships

### 4.3 Direction Rules

#### 4.3.1 Directed Relationships

> Directed relationships have explicit source and target endpoints.

- Direction is part of the relationship semantics
- Reversing direction creates a different relationship
- Direction consistency maintained across evolution

#### 4.3.2 Undirected Relationships

> Undirected relationships treat endpoints symmetrically.

- No source/target distinction
- Bidirectional semantics
- Normalization ensures consistent representation

### 4.4 Cardinality Rules

#### 4.4.1 One-to-One

> Some relationship types allow only one instance per endpoint pair.

- Enforced at domain level
- Violations require normalization or rejection

#### 4.4.2 One-to-Many

> Some relationship types allow multiple instances from one endpoint.

- Cardinality limits defined per type
- Limits enforced through domain rules

#### 4.4.3 Many-to-Many

> Some relationship types allow unrestricted connections.

- No cardinality limits by default
- Semantic constraints may apply

### 4.5 Lifecycle Rules

#### 4.5.1 Creation

> New relationships must satisfy all domain invariants.

- Endpoint compatibility verified
- Type validity confirmed
- Cardinality constraints checked
- Direction rules enforced

#### 4.5.2 Evolution

> Relationships evolve through domain rules, not arbitrary changes.

- Type changes require domain justification
- Endpoint changes follow evolution rules
- Direction changes create new relationship instances

#### 4.5.3 Deactivation

> Relationships may be deactivated, not deleted.

- Deactivation preserves historical record
- Archived relationships remain queryable
- Deactivation is a domain decision, not physical removal

### 4.6 Semantic Consistency Rules

#### 4.6.1 Semantic Integrity

> Relationship semantics must remain consistent across all operations.

- Meaning of relationship preserved through evolution
- Semantic contradictions resolved through normalization
- Context-aware semantic validation

#### 4.6.2 Canonical Representation

> Equivalent relationships have canonical representation.

- Normalization ensures consistent representation
- Deduplication removes redundant instances
- Canonical form aids comparison and querying

## 5. Domain Invariants

### 5.1 Valid Endpoint Invariant

> Every Relationship connects two valid Entities.

This is the foundational invariant. If violated, Relationship creation is rejected.

### 5.2 Relationship Type Invariant

> Every Relationship has a valid Relationship Type.

Types are drawn from the domain registry. Invalid types are rejected.

### 5.3 Semantic Integrity Invariant

> Relationship semantics remain internally consistent across all state transitions.

Contradictory semantics are resolved through normalization rules, not ignored.

### 5.4 Structural Integrity Invariant

> Relationship structure maintains domain consistency.

Cardinality constraints, direction rules, and endpoint compatibility always hold.

### 5.5 Canonical Representation Invariant

> Equivalent relationships have a single canonical representation.

Normalization ensures no semantic duplicates exist in the domain model.

### 5.6 Domain Consistency Invariant

> All relationship operations maintain domain consistency.

No operation violates existing invariants. New operations must be validated against all invariants.

### 5.7 Invariant Hierarchy

```
Domain Consistency
    │
    ├── Semantic Integrity
    │       │
    │       └── Relationship Type
    │               │
    │               └── Valid Endpoint
    │
    └── Structural Integrity
            │
            └── Canonical Representation
```

All invariants are:

- **Universal**: Apply to all Relationships
- **Context Independent**: Not dependent on specific domain scenarios
- **Always Enforced**: No bypass mechanism exists

### 5.8 Invariant Extension Principle

> New invariants may be introduced in future versions only through architectural evolution while preserving backward compatibility, unless revised by ADR.

Any new invariant must:

- Not violate existing invariants
- Be justified by domain necessity
- Pass D4 principle consistency review
- Be documented with ADR if it changes existing behavior

## 6. Internal Composition

### 6.1 Architecture Overview

```
RelationshipEngine (Public Facade)
│
├── Identity Capability          — Relationship identity management
├── Validation Capability        — Domain rule validation
├── Semantic Capability          — Semantic interpretation and consistency
├── Lifecycle Capability         — Relationship state transitions
├── Normalization Capability     — Canonical representation
└── Invariant Capability         — Domain invariant verification
```

RelationshipEngine is a **Facade**. Its internal composition is private. Service depends only on the public contract.

### 6.2 Capabilities

#### Identity Capability

- Manages Relationship identity (unique identifier)
- Ensures relationship uniqueness
- Handles relationship resolution
- Maintains relationship history

#### Validation Capability

- Validates Relationship against domain rules
- Checks endpoint compatibility
- Verifies type validity
- Enforces cardinality constraints

#### Semantic Capability

- Interprets relationship semantics
- Maintains semantic consistency
- Analyzes relationship networks
- Provides context-aware semantic analysis

#### Lifecycle Capability

- Manages relationship state transitions
- Applies evolution rules
- Handles deactivation workflows
- Manages historical records

#### Normalization Capability

- Normalizes relationship representations
- Deduplicates semantically identical relationships
- Ensures canonical representation
- Handles direction normalization

#### Invariant Capability

- Verifies domain invariants
- Protects semantic integrity
- Ensures structural consistency
- Maintains domain purity

### 6.3 Composition Principles

| Principle | Description |
|-----------|-------------|
| **Composition Over Inheritance** | Internal capabilities use composition. Inheritance prohibited. |
| **Single Responsibility** | Each capability owns exactly one domain concern. |
| **Internal Collaboration Only** | Capabilities collaborate internally. Service never sees them. |
| **Replaceable Internal Capabilities** | Capabilities can be replaced without changing public contract. |
| **Stable Public Facade** | Public contract is the only dependency point for Service. |

## 7. Extension Points

### 7.1 Allowed Extensions

The following are architecturally open for extension:

| Extension Type | Category | Description |
|----------------|----------|-------------|
| **New Relationship Domain Capability** | B | Add new Capability for domain evolution |
| **Extending Existing Capability** | B | Enhance existing Capability functionality |
| **Relationship Type Expansion** | C | Add new Relationship Types to domain registry |
| **Semantic Rule Expansion** | C | Add new semantic interpretation rules |
| **Normalization Algorithm Expansion** | C | Extend normalization capabilities |

### 7.2 Architecturally Closed

The following are closed and require ADR to change:

| Closed Aspect | Reason |
|---------------|--------|
| **Domain Scope** | Relationship domain is fixed by architecture |
| **Layer Responsibility** | Engine layer cannot own workflow or persistence |
| **Engine Dependency Model** | Engine calls Repository only, never other Engines |
| **Public Contract Stability** | Contract changes require ADR |
| **Domain Invariants** | Existing invariants cannot be weakened |

### 7.3 Extension Principles

| Principle | Description |
|-----------|-------------|
| **Open for Domain Evolution** | New domain rules and capabilities can be added |
| **Closed for Architectural Responsibility** | Layer boundaries cannot be crossed |
| **Stable Public Contract** | Extensions must not break existing contract |
| **No New Engine Without Independent Capability** | No new Engine unless a completely independent Domain Capability emerges |

## 8. Testing Strategy

### 8.1 Testing Principles

| Principle | Description |
|-----------|-------------|
| **Public Contract First** | Tests verify public contract, not internal implementation |
| **Rule-Driven Testing** | Tests verify domain rules are enforced |
| **Invariant Protection** | Tests ensure invariants are never violated |
| **Stateless Verification** | Same input always produces same result |
| **Boundary Testing** | Tests verify Engine-Repository boundary |
| **Extension Compatibility** | New capabilities must not break existing tests |

### 8.2 Testing Layers

#### Capability Tests

| Capability | Test Focus |
|------------|------------|
| **Identity Capability** | Relationship uniqueness, identity resolution, history maintenance |
| **Validation Capability** | Endpoint compatibility, type validity, cardinality enforcement |
| **Semantic Capability** | Semantic consistency, interpretation accuracy, network analysis |
| **Lifecycle Capability** | State transitions, evolution rules, deactivation handling |
| **Normalization Capability** | Canonical representation, deduplication, direction normalization |
| **Invariant Capability** | All six invariants verified, hierarchy maintained |

#### Facade Tests

- Public contract stability
- Stateless verification
- Deterministic behavior
- Domain Result (not protocol Result)

#### Regression Tests

- Existing domain rules continue to work
- No invariant violations from new code
- Extension compatibility verified

#### Boundary Tests

- Engine-Repository boundary (RelationshipEngine calls Repository only)
- Engine-Engine boundary (no cross-Engine calls)
- Engine-Service boundary (Service orchestrates, Engine decides)

### 8.3 Test Dependencies

```
RelationshipEngine Test
├── RelationshipEngine (SUT)
├── Repository Mock (returns Domain Models)
├── Domain Result Assertion
└── Domain Error Assertion
```

- Tests mock Repository — do not use real database
- Tests verify Engine in isolation — no other Engines involved
- Tests do not involve Service layer — Engine tested directly

### 8.4 Verification Requirements

Tests must verify:

- **Domain consistency** — Relationship domain rules enforced
- **Frozen rules** — All six invariants maintained
- **No Repository dependency** — Tests do not depend on persistence
- **No Service dependency** — Engine tested independently
- **No Engine dependency** — No cross-Engine calls in tests
