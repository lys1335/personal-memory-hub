## 1. Purpose

### 1.1 Core Identity

EntityEngine is the **Entity Domain semantic consistency owner**.

EntityEngine is a stateless domain engine responsible for Entity identity resolution, canonical entity semantics, identity consolidation, and entity evolution decisions.

It owns:

- Entity identity resolution
- Canonical entity semantics
- Identity consolidation decisions
- Entity evolution rules
- Alias management
- Metadata consistency

EntityEngine is a **Domain Engine**, not a persistence wrapper. It does not call databases directly. It operates on Domain Models provided by Repository.

This document adheres to D4 principles:

- **One Domain Capability → One Engine**: EntityEngine owns Entity domain only
- **Engine is a Stable Facade**: Public contract is stable, internal composition is private
- **Domain Result, Not Protocol Result**: Returns domain-level results
- **No Cross-Engine Calls**: EntityEngine never calls other Engines
- **Domain Consistency, Not Business Consistency**: EntityEngine ensures domain invariants, Service ensures business consistency
- **Algorithm Isolation**: Domain algorithms are isolated within EntityEngine

### 1.2 Relationship with MemoryEngine

EntityEngine and MemoryEngine are sibling Domain Engines under the same architectural layer:

- **EntityEngine** owns Entity identity, canonical semantics, and evolution
- **MemoryEngine** owns Memory semantic consistency, evidence integrity, and lifecycle

They collaborate through Service orchestration. EntityEngine never calls MemoryEngine. MemoryEngine never calls EntityEngine.

Entity references are immutable — when EntityService creates Memory, it passes EntityID to MemoryEngine. MemoryEngine stores the reference. EntityEngine owns the identity resolution logic.

## 2. Responsibilities

### 2.1 Entity State Evaluation

EntityEngine evaluates Entity state for domain purposes:

- Identity resolution (input → EntityID)
- State validity (Active, Archived, Merged)
- Canonical entity determination
- Alias conflict detection

### 2.2 Entity Rule Validation

EntityEngine validates that each Entity satisfies domain invariants:

- Canonical Identity rule
- Alias uniqueness rule
- Entity Type validity rule
- State transition legality rule

### 2.3 Entity Consistency Enforcement

EntityEngine enforces domain consistency:

- Single Canonical Identity per EntityID
- Identity continuity across evolution
- Alias non-conflict guarantee
- Metadata consistency

### 2.4 Entity Evolution Decision

EntityEngine determines Entity evolution actions:

- Canonical Name selection (based on evidence accumulation)
- Alias addition/removal decisions
- Identity Consolidation feasibility assessment
- State transition approval (Active → Archived, etc.)

### 2.5 Derived Domain Information

EntityEngine derives domain information from Entity state:

- Canonical Name derivation
- Alias resolution results
- Entity Type classification
- Identity graph relationships

### 2.6 Canonical Entity Semantics

EntityEngine owns canonical entity semantics:

- Definition of Current Best Identity
- Canonical Name selection rules
- Alias hierarchy management
- Identity continuity preservation

### 2.7 Explicitly NOT Owned

EntityEngine does NOT own:

- **Workflow orchestration** — EntityService orchestrates multi-step workflows
- **Transaction management** — Service owns transaction boundaries
- **Repository coordination** — Repository owns data access
- **Persistence** — Repository handles database operations
- **API exposure** — Entry Layer handles protocol (D5)
- **AI provider management** — Service manages AI integration
- **Memory domain** — MemoryEngine owns Memory
- **Relationship graph** — RelationshipEngine owns Relationships
- **Search/Projection** — SearchEngine/ProjectionEngine own retrieval
- **Cross-Engine coordination** — Service coordinates between Engines

## 3. Public Contract

EntityEngine's public contract follows these capabilities:

### 3.1 Evaluate Entity State

EntityEngine evaluates the current state of an Entity for domain purposes.

**Principle**: Answers domain questions about Entity state. Does not modify state.

### 3.2 Validate Entity

EntityEngine validates that an Entity satisfies domain invariants.

**Principle**: Returns validation result. Does not enforce persistence.

### 3.3 Evaluate Entity Evolution Decision

EntityEngine evaluates what evolution action is appropriate for an Entity.

**Principle**: Returns domain decision. Does not execute evolution.

### 3.4 Verify Domain Invariants

EntityEngine verifies that Entity domain invariants hold.

**Principle**: Invariant verification is deterministic and stateless.

### 3.5 Derive Domain Information

EntityEngine derives domain information from Entity state.

**Principle**: Derivation is based on domain rules, not protocol needs.

### 3.6 Contract Principles

| Principle | Description |
|-----------|-------------|
| **Capability-Oriented** | Methods organized by domain capability, not CRUD |
| **Stateless** | No mutable instance state |
| **Deterministic** | Same input → same Domain Result |
| **Domain-Oriented** | Returns DomainResult, not protocol types |
| **Side-Effect Free** | No direct Repository modifications |
| **Explicit Result** | Success, failure, or required action always explicit |

## 4. Domain Rules

### 4.1 Identity Rules

#### 4.1.1 Canonical Identity

> Every Entity has exactly one Canonical Identity (EntityID).

- EntityID is stable and immutable
- EntityID never changes throughout Entity existence
- EntityID is the anchor for all identity operations

#### 4.1.2 Alias

> Aliases are alternative names that resolve to the Canonical Identity.

- Multiple aliases may exist per Entity
- Aliases must not conflict with other Entities
- Alias resolution returns the Canonical EntityID

#### 4.1.3 Identity Continuity

> Identity continuity is preserved across all Entity operations.

- Historical identity information is never lost
- Identity evolution maintains traceability
- Past aliases remain resolvable through history

### 4.2 Entity Type Rules

#### 4.2.1 Type Validity

> Entity Type must be from the approved domain type registry.

- Types are domain-defined, not protocol-defined
- Type changes follow evolution rules
- Type invalidation requires domain justification

#### 4.2.2 Type Evolution

> Entity Type may evolve through domain rules.

- Type evolution is tracked as domain history
- Evolution decisions are made by EntityEngine
- Service executes type evolution after validation

### 4.3 State Rules

#### 4.3.1 Active

> Active Entities participate in current domain operations.

- Active is the default state for new Entities
- Active Entities have current Canonical Name
- Active Entities may have aliases

#### 4.3.2 Archived

> Archived Entities are retained for historical reference.

- Archival preserves identity history
- Archived Entities remain resolvable
- Archival is a domain decision, not deletion

#### 4.3.3 Merged

> Merged Entities have undergone Identity Consolidation.

- Merged Entities contribute to Canonical Identity
- Historical merged Entities cannot act independently
- Only canonical active entities participate in future merge decisions

### 4.4 Evolution Rules

#### 4.4.1 Entity Evolution

> Entity evolves through domain rules, not arbitrary changes.

- Evolution is Identity Evolution, not Lifecycle
- Canonical Name updates based on evidence accumulation
- Alias additions follow conflict resolution rules

**Note**: Use "Entity Evolution" terminology. Do NOT use "Entity Lifecycle".

#### 4.4.2 Identity Preservation

> Evolution never breaks identity continuity.

- EntityID remains constant through evolution
- Historical identity information is preserved
- Evolution decisions maintain traceability

#### 4.4.3 Historical Continuity

> All identity changes maintain historical continuity.

- Past states remain queryable
- Identity evolution is monotonic in information
- No identity information is lost through evolution

### 4.5 Metadata Rules

#### 4.5.1 Canonical Name

> Canonical Name represents the Current Best Identity.

- Selected through evidence accumulation
- Updated through domain rules
- Not arbitrary — requires domain justification

#### 4.5.2 Metadata Consistency

> All Entity metadata maintains domain consistency.

- Metadata updates follow evolution rules
- Consistency verified by EntityEngine
- Service executes validated metadata changes

### 4.6 Semantic Rules

#### 4.6.1 AI Provides Candidates

> AI systems provide candidate suggestions for Entity evolution.

- AI suggests Canonical Name candidates
- AI proposes Alias additions
- AI recommends Identity Consolidation

#### 4.6.2 EntityEngine Provides Domain Decisions

> EntityEngine makes final domain decisions based on rules.

- AI suggestions are evaluated against domain rules
- EntityEngine validates candidate appropriateness
- Domain invariants override AI suggestions

**Principle**: AI provides candidates. EntityEngine provides domain decisions.

## 5. Domain Invariants

### 5.1 Identity Is Immutable

> EntityID never changes after creation.

This is the foundational invariant. If violated, Entity creation is rejected.

### 5.2 Single Canonical Identity

> Each Entity has exactly one Canonical Identity at any time.

No ambiguity in identity resolution. Alias conflicts are resolved by domain rules.

### 5.3 Valid Domain State

> Entity state transitions follow domain rules only.

Invalid state transitions are rejected. State changes require domain justification.

### 5.4 Evolution Preserves Identity

> Entity evolution never breaks identity continuity.

All evolution operations maintain traceability to original EntityID.

### 5.5 Canonical Entity Uniqueness

> Only one active canonical Entity exists per identity group.

Historical merged entities cannot act independently. Only canonical active entities participate in future merge decisions.

### 5.6 Historical Traceability

> All identity changes maintain complete historical traceability.

Past states remain queryable. Identity evolution is fully auditable.

### 5.7 Invariant Extension Principle

> New invariants may be introduced in future versions only through architectural evolution while preserving backward compatibility, unless revised by ADR.

Any new invariant must:

- Not violate existing invariants
- Be justified by domain necessity
- Pass D4 principle consistency review
- Be documented with ADR if it changes existing behavior

## 6. Internal Composition

### 6.1 Architecture Overview

```
EntityEngine (Public Facade)
│
├── Identity Capability       — Canonical Identity management
├── State Capability          — Entity state evaluation
├── Evolution Capability      — Entity evolution decisions
├── Validation Capability     — Domain rule validation
├── Semantic Capability       — Canonical semantics
└── Invariant Capability     — Domain invariant verification
```

EntityEngine is a **Facade**. Its internal composition is private. Service depends only on the public contract.

### 6.2 Capabilities

#### Identity Capability

- Manages Canonical Identity (EntityID)
- Handles alias resolution
- Ensures identity uniqueness
- Maintains identity continuity

#### State Capability

- Evaluates Entity state (Active, Archived, Merged)
- Validates state transitions
- Determines current best identity
- Manages state history

#### Evolution Capability

- Decides Entity evolution actions
- Manages Canonical Name evolution
- Handles alias addition/removal
- Assesses Identity Consolidation feasibility

#### Validation Capability

- Validates Entity against domain rules
- Checks alias conflicts
- Verifies type validity
- Ensures metadata consistency

#### Semantic Capability

- Manages canonical entity semantics
- Determines Current Best Identity
- Handles alias hierarchy
- Maintains semantic consistency

#### Invariant Capability

- Verifies domain invariants
- Protects identity immutability
- Ensures evolution preserves identity
- Maintains historical traceability

### 6.3 Composition Principles

| Principle | Description |
|-----------|-------------|
| **Composition Over Inheritance** | Internal capabilities use composition. Inheritance prohibited. |
| **Single Responsibility** | Each capability owns exactly one domain concern. |
| **Internal Collaboration Only** | Capabilities collaborate internally. Service never sees them. |
| **Replaceable Internal Capabilities** | Capabilities can be replaced without changing public contract. |
| **Stable Public Facade** | Public contract is the only dependency point for Service. |

## 7. Extension Points

### 7.1 Allowed Extensions

The following are architecturally open for extension:

| Extension Type | Category | Description |
|----------------|----------|-------------|
| **New Entity Domain Capability** | B | Add new Capability for domain evolution |
| **Extending Existing Capability** | B | Enhance existing Capability functionality |
| **Entity Type Expansion** | C | Add new Entity Types to domain registry |
| **Evolution Rule Expansion** | C | Add new evolution rules |
| **AI-Assisted Semantic Expansion** | C | Extend semantic capabilities with AI assistance |

### 7.2 Architecturally Closed

The following are closed and require ADR to change:

| Closed Aspect | Reason |
|---------------|--------|
| **Domain Scope** | Entity domain is fixed by architecture |
| **Layer Responsibility** | Engine layer cannot own workflow or persistence |
| **Engine Dependency Model** | Engine calls Repository only, never other Engines |
| **Public Contract Stability** | Contract changes require ADR |
| **Domain Invariants** | Existing invariants cannot be weakened |

### 7.3 Extension Principles

| Principle | Description |
|-----------|-------------|
| **Open for Domain Evolution** | New domain rules and capabilities can be added |
| **Closed for Architectural Responsibility** | Layer boundaries cannot be crossed |
| **Stable Public Contract** | Extensions must not break existing contract |
| **No New Engine Without Independent Capability** | No new Engine unless a completely independent Domain Capability emerges |

## 8. Testing Strategy

### 8.1 Testing Principles

| Principle | Description |
|-----------|-------------|
| **Public Contract First** | Tests verify public contract, not internal implementation |
| **Rule-Driven Testing** | Tests verify domain rules are enforced |
| **Invariant Protection** | Tests ensure invariants are never violated |
| **Stateless Verification** | Same input always produces same result |
| **Boundary Testing** | Tests verify Engine-Repository boundary |
| **Extension Compatibility** | New capabilities must not break existing tests |

### 8.2 Testing Layers

#### Capability Tests

| Capability | Test Focus |
|------------|------------|
| **Identity Capability** | Canonical Identity uniqueness, alias resolution, identity continuity |
| **State Capability** | State transitions, state validation, current best identity |
| **Evolution Capability** | Evolution decisions, Canonical Name updates, alias management |
| **Validation Capability** | Domain rule validation, alias conflict detection, type validity |
| **Semantic Capability** | Canonical semantics, Current Best Identity determination |
| **Invariant Capability** | Identity immutability, evolution preserves identity, historical traceability |

#### Facade Tests

- Public contract stability
- Stateless verification
- Deterministic behavior
- Domain Result (not protocol Result)

#### Regression Tests

- Existing domain rules continue to work
- No invariant violations from new code
- Extension compatibility verified

#### Boundary Tests

- Engine-Repository boundary (EntityEngine calls Repository only)
- Engine-Engine boundary (no cross-Engine calls)
- Engine-Service boundary (Service orchestrates, Engine decides)

### 8.3 Test Dependencies

```
EntityEngine Test
├── EntityEngine (SUT)
├── Repository Mock (returns Domain Models)
├── Domain Result Assertion
└── Domain Error Assertion
```

- Tests mock Repository — do not use real database
- Tests verify Engine in isolation — no other Engines involved
- Tests do not involve Service layer — Engine tested directly

### 8.4 Verification Requirements

Tests must verify:

- **Domain consistency** — Entity domain rules enforced
- **Frozen rules** — Identity immutability, single canonical identity
- **No Repository dependency** — Tests do not depend on persistence
- **No Service dependency** — Engine tested independently
- **No Engine dependency** — No cross-Engine calls in tests
