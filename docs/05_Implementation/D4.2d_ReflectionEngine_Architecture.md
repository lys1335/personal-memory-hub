## 1. Purpose

### 1.1 Core Identity

ReflectionEngine is the **Reflection Domain semantic consistency owner**.

ReflectionEngine is a stateless domain engine responsible for Reflection semantic validation, candidate evaluation, knowledge evolution validation, reflection consistency, knowledge consolidation rules, and reflection domain invariants.

It owns:

- Reflection semantic validation
- Reflection candidate evaluation
- Knowledge evolution validation
- Reflection consistency
- Knowledge consolidation rules
- Reflection domain invariants

ReflectionEngine is a **Domain Engine**, not a persistence wrapper. It does not call databases directly. It operates on Domain Models provided by Repository.

This document adheres to D4 principles:

- **One Domain Capability → One Engine**: ReflectionEngine owns Reflection domain only
- **Engine is a Stable Facade**: Public contract is stable, internal composition is private
- **Domain Result, Not Protocol Result**: Returns domain-level results
- **No Cross-Engine Calls**: ReflectionEngine never calls other Engines
- **Domain Consistency, Not Business Consistency**: ReflectionEngine ensures domain invariants, Service ensures business consistency
- **Algorithm Isolation**: Domain algorithms are isolated within ReflectionEngine

### 1.2 Relationship with Other Engines

ReflectionEngine, EntityEngine, MemoryEngine, and RelationshipEngine are sibling Domain Engines under the same architectural layer:

- **ReflectionEngine** owns Reflection semantics, candidate evaluation, and knowledge evolution
- **EntityEngine** owns Entity identity, canonical semantics, and evolution
- **MemoryEngine** owns Memory semantic consistency, evidence integrity, and lifecycle
- **RelationshipEngine** owns Relationship semantics, validity, and consistency

ReflectionEngine operates on Memories and Entities. It validates reflection candidates and ensures knowledge evolution follows domain rules. It never calls MemoryEngine, EntityEngine, or RelationshipEngine directly. Service coordinates between Engines.

## 2. Responsibilities

### 2.1 Reflection Semantic Validation

ReflectionEngine validates that each Reflection satisfies domain invariants:

- Reflection candidate is semantically coherent
- Evidence chain is complete and valid
- Knowledge evolution follows domain rules
- Reflection output is domain-consistent

### 2.2 Reflection Candidate Evaluation

ReflectionEngine evaluates reflection candidates for domain purposes:

- Candidate semantic quality assessment
- Evidence strength analysis
- Knowledge evolution appropriateness
- Consolidation feasibility

### 2.3 Knowledge Evolution Validation

ReflectionEngine validates knowledge evolution actions:

- Evolution follows configured Knowledge Evolution Model
- Evidence requirements satisfied
- Semantic integrity preserved
- Historical traceability maintained

### 2.4 Reflection Consistency

ReflectionEngine ensures reflection consistency:

- Idempotent reflection operations
- Consistent candidate generation
- Stable evolution decisions
- Reproducible results

### 2.5 Knowledge Consolidation Rules

ReflectionEngine enforces knowledge consolidation rules:

- Consolidation criteria met
- Evidence chain preserved during consolidation
- Semantic content not lost during consolidation
- Consolidation decisions domain-justified

### 2.6 Reflection Domain Invariants

ReflectionEngine protects reflection domain invariants:

- Evidence requirement invariant
- Semantic coherence invariant
- Evolution monotonicity invariant
- Traceability invariant
- Idempotency invariant

### 2.7 Explicitly NOT Owned

ReflectionEngine does NOT own:

- **Workflow orchestration** — ReflectionService orchestrates multi-step workflows
- **Task scheduling** — Task Runtime handles scheduling
- **Repository access** — Repository owns data access
- **Persistence** — Repository handles database operations
- **Transaction management** — Service owns transaction boundaries
- **Context building** — ContextBuilder handles context assembly
- **LLM invocation** — Service manages AI provider communication
- **API exposure** — Entry Layer handles protocol (D5)
- **Entity identity** — EntityEngine owns Entity identity
- **Memory semantics** — MemoryEngine owns Memory consistency
- **Relationship semantics** — RelationshipEngine owns Relationship consistency
- **Search/projection** — SearchEngine/ProjectionEngine own retrieval
- **Cross-Engine coordination** — Service coordinates between Engines

## 3. Public Contract Principles

ReflectionEngine's public contract follows these principles:

### 3.1 Capability-Oriented

Methods are organized by domain capability, not by CRUD operations.

### 3.2 Stateless

ReflectionEngine has no mutable instance state. All state comes from Repository reads.

### 3.3 Deterministic

Given the same input Memories and context, ReflectionEngine always produces the same Domain Result.

### 3.4 Domain-Oriented

Returns domain-level results (DomainResult, DomainError), not protocol-specific types.

### 3.5 Side-Effect Free

ReflectionEngine does not directly modify Repository data. It returns domain commands that Service executes.

### 3.6 Explicit Result

Every method returns an explicit result indicating success, failure, or required action.

### 3.7 Repository Agnostic

ReflectionEngine operates on Domain Models, not database schemas.

### 3.8 Workflow Independent

ReflectionEngine makes domain decisions only. It does not orchestrate workflows.

### 3.9 Engine Independent

ReflectionEngine never calls other Engines. All Engine coordination happens at Service layer.

## 4. Domain Rules

### 4.1 Knowledge Evolution Model

#### 4.1.1 Open-Ended Evolution

> Knowledge Evolution Model is open-ended. Architecture must not depend on fixed hierarchy names.

- Lower Abstraction → Higher Abstraction progression
- Increasing Abstraction through evolution
- No predefined upper limit on knowledge levels
- Concrete level names (Observation, Pattern, Belief) are examples only

#### 4.1.2 Evidence Foundation

> Observation (Evidence) is the immutable foundation of the Knowledge Pyramid.

- All higher knowledge levels derive from Evidence
- Evidence cannot be modified or deleted
- Evidence chain must be complete for evolution

#### 4.1.3 Model Configuration

> ReflectionEngine validates evolution against the configured Knowledge Evolution Model.

- Model defines valid transitions between knowledge levels
- Model specifies evidence requirements per transition
- Model may evolve without architectural changes

#### 4.1.4 Evolution Validation

> ReflectionEngine validates whether evolution follows the configured Knowledge Evolution Model, not whether it reaches specific level names.

- Validation is model-aware, not name-dependent
- Future knowledge levels supported without architecture modification
- Evolution rules enforced regardless of level naming

### 4.2 Candidate Evaluation Rules

#### 4.2.1 Evidence Completeness

> Every reflection candidate must have complete evidence chain.

- Evidence must trace to original Observations
- No gaps in evidence chain permitted
- Evidence strength assessed quantitatively

#### 4.2.2 Semantic Coherence

> Candidates must demonstrate semantic coherence.

- Logical consistency within candidate
- Alignment with existing knowledge
- No contradictory assertions

#### 4.2.3 Evolution Appropriateness

> Candidates must represent appropriate knowledge evolution.

- Advancement to higher abstraction level
- Meaningful semantic enrichment
- Not mere repetition of existing knowledge

### 4.3 Consolidation Rules

#### 4.3.1 Consolidation Criteria

> Knowledge consolidation follows explicit domain rules.

- Evidence overlap sufficient
- Semantic redundancy identified
- Consolidation improves clarity

#### 4.3.2 Evidence Preservation

> Consolidation never loses evidence.

- All supporting evidence preserved
- Evidence chain maintained
- Historical traceability guaranteed

#### 4.3.3 Semantic Integrity

> Consolidation preserves semantic integrity.

- No semantic content lost
- Meaning enhanced through consolidation
- Contradictions resolved appropriately

### 4.4 Idempotency Rules

#### 4.4.1 Deterministic Output

> Same input produces same reflection output.

- No randomness in domain decisions
- Consistent candidate generation
- Stable evolution decisions

#### 4.4.2 Repeat Execution Safety

> Reflection can be executed multiple times safely.

- Idempotent domain operations
- No duplicate candidates created
- State unchanged by redundant execution

### 4.5 Traceability Rules

#### 4.5.1 Full Chain Preservation

> Every reflection output traces to original evidence.

- Evidence chain never broken
- Historical reconstruction always possible
- All derivation steps documented

#### 4.5.2 Evolution History

> Knowledge evolution history maintained completely.

- All evolution steps recorded
- Historical states queryable
- Evolution path auditable

## 5. Domain Invariants

### 5.1 Evidence Requirement Invariant

> Every reflection candidate must have complete, valid evidence chain.

This is the foundational invariant. If violated, candidate is rejected.

### 5.2 Semantic Coherence Invariant

> Reflection candidates maintain semantic coherence throughout evolution.

Contradictory semantics resolved through consolidation rules, not ignored.

### 5.3 Evolution Monotonicity

> Knowledge evolution is monotonic in abstraction and clarity.

Each evolution step produces equal or greater semantic clarity. Never less.

### 5.4 Traceability Preservation

> Evidence chain preserved through all reflection operations.

Even when knowledge is consolidated, evidence origin remains traceable.

### 5.5 Idempotency Invariant

> Reflection operations are idempotent.

Same input always produces same output. Multiple executions safe.

### 5.6 Model Independence

> ReflectionEngine independent from concrete knowledge level names.

Architecture validates evolution against configured model, not fixed hierarchy.

### 5.7 Invariant Hierarchy

```
Domain Consistency
    │
    ├── Semantic Coherence
    │       │
    │       └── Evidence Requirement
    │               │
    │               └── Evolution Monotonicity
    │
    └── Operational Integrity
            │
            ├── Traceability Preservation
            ├── Idempotency
            └── Model Independence
```

All invariants are:

- **Universal**: Apply to all Reflection operations
- **Context Independent**: Not dependent on specific domain scenarios
- **Always Enforced**: No bypass mechanism exists

### 5.8 Invariant Extension Principle

> New invariants may be introduced in future versions only through architectural evolution while preserving backward compatibility, unless revised by ADR.

Any new invariant must:

- Not violate existing invariants
- Be justified by domain necessity
- Pass D4 principle consistency review
- Be documented with ADR if it changes existing behavior

## 6. Internal Composition

### 6.1 Architecture Overview

```
ReflectionEngine (Public Facade)
│
├── Validation Capability      — Domain rule validation
├── Semantic Capability        — Semantic interpretation and consistency
├── Evolution Capability       — Knowledge evolution decisions
├── Candidate Capability       — Candidate evaluation and generation
├── Consistency Capability     — Reflection consistency assurance
├── Consolidation Capability   — Knowledge consolidation rules
└── Invariant Capability       — Domain invariant verification
```

ReflectionEngine is a **Facade**. Its internal composition is private. Service depends only on the public contract.

### 6.2 Capabilities

- Validates reflection candidates against domain rules
- Checks evidence completeness
- Verifies semantic coherence
- Ensures evolution appropriateness

#### Semantic Capability

- Interprets reflection semantics
- Maintains semantic consistency

#### Evolution Capability

- Decides knowledge evolution actions
- Validates evolution against configured model
- Ensures monotonic abstraction increase
- Manages evolution history

#### Candidate Capability

- Validates candidate quality

#### Consistency Capability

- Ensures idempotent operations
- Maintains deterministic behavior
- Verifies repeat execution safety
- Stabilizes reflection output

#### Consolidation Capability

- Applies consolidation rules
- Preserves evidence during consolidation
- Resolves semantic contradictions
- Maintains semantic integrity

#### Invariant Capability

- Verifies domain invariants
- Protects evidence requirement
- Ensures evolution monotonicity
- Maintains model independence

## 7. Extension Points

### 7.1 Allowed Extensions

The following are architecturally open for extension:

| Extension Type | Category | Description |
|----------------|----------|-------------|
| **New Reflection Domain Capability** | B | Add new Capability for domain evolution |
| **Extending Existing Capability** | B | Enhance existing Capability functionality |
| **Knowledge Evolution Model Changes** | C | Modify configured evolution model |
| **Candidate Evaluation Rules** | C | Add new evaluation criteria |
| **Consolidation Algorithm Expansion** | C | Extend consolidation capabilities |

### 7.2 Architecturally Closed

The following are closed and require ADR to change:

| Closed Aspect | Reason |
|---------------|--------|
| **Domain Scope** | Reflection domain is fixed by architecture |
| **Layer Responsibility** | Engine layer cannot own workflow or persistence |
| **Engine Dependency Model** | Engine calls Repository only, never other Engines |
| **Public Contract Stability** | Contract changes require ADR |
| **Domain Invariants** | Existing invariants cannot be weakened |
| **Knowledge Evolution Model Independence** | Must remain independent from fixed hierarchy names |

### 7.3 Extension Principles

| Principle | Description |
|-----------|-------------|
| **Open for Domain Evolution** | New domain rules and capabilities can be added |
| **Closed for Architectural Responsibility** | Layer boundaries cannot be crossed |
| **Stable Public Contract** | Extensions must not break existing contract |
| **No New Engine Without Independent Capability** | No new Engine unless a completely independent Domain Capability emerges |

## 8. Testing Strategy

### 8.1 Testing Principles

| Principle | Description |
|-----------|-------------|
| **Public Contract First** | Tests verify public contract, not internal implementation |
| **Rule-Driven Testing** | Tests verify domain rules are enforced |
| **Invariant Protection** | Tests ensure invariants are never violated |
| **Stateless Verification** | Same input always produces same result |
| **Boundary Testing** | Tests verify Engine-Repository boundary |
| **Extension Compatibility** | New capabilities must not break existing tests |

### 8.2 Testing Layers

#### Capability Tests

| Capability | Test Focus |
|------------|------------|
| **Validation Capability** | Evidence completeness, semantic coherence, evolution appropriateness |
| **Semantic Capability** | Semantic consistency, interpretation accuracy, knowledge relationships |
| **Evolution Capability** | Model compliance, monotonic abstraction, evolution history |
| **Candidate Capability** | Candidate evaluation, evidence strength, quality assessment |
| **Consistency Capability** | Idempotency, deterministic behavior, repeat execution safety |
| **Consolidation Capability** | Evidence preservation, semantic integrity, contradiction resolution |
| **Invariant Capability** | All seven invariants verified, hierarchy maintained |

#### Facade Tests

- Public contract stability
- Stateless verification
- Deterministic behavior
- Domain Result (not protocol Result)

#### Regression Tests

- Existing domain rules continue to work
- No invariant violations from new code
- Extension compatibility verified

#### Boundary Tests

- Engine-Repository boundary (ReflectionEngine calls Repository only)
- Engine-Engine boundary (no cross-Engine calls)
- Engine-Service boundary (Service orchestrates, Engine decides)

### 8.3 Test Dependencies

```
ReflectionEngine Test
├── ReflectionEngine (SUT)
├── Repository Mock (returns Domain Models)
├── Domain Result Assertion
└── Domain Error Assertion
```

- Tests mock Repository — do not use real database
- Tests verify Engine in isolation — no other Engines involved
- Tests do not involve Service layer — Engine tested directly

### 8.4 Verification Requirements

Tests must verify:

- **Domain consistency** — Reflection domain rules enforced
- **Frozen rules** — All seven invariants maintained
- **No Repository dependency** — Tests do not depend on persistence
- **No Service dependency** — Engine tested independently
- **No Engine dependency** — No cross-Engine calls in tests
