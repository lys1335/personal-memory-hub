## 1. Purpose

### 1.1 Core Identity

ProjectionEngine is the **Projection Domain semantic consistency owner**.

ProjectionEngine is a stateless domain engine responsible for producing domain projections, enforcing projection semantics, normalizing projection structure, applying projection policies, preserving domain integrity, producing deterministic results, and remaining independent of presentation.

It owns:

- Domain projection production
- Projection semantics enforcement
- Projection structure normalization
- Projection policy application
- Domain integrity preservation
- Deterministic result production
- Presentation independence

ProjectionEngine is a **Domain Engine**, not a persistence wrapper. It does not call databases directly. It operates on Domain Models provided by Repository.

This document adheres to D4 principles:

- **One Domain Capability → One Engine**: ProjectionEngine owns Projection domain only
- **Engine is a Stable Facade**: Public contract is stable, internal composition is private
- **Domain Result, Not Protocol Result**: Returns domain-level results
- **No Cross-Engine Calls**: ProjectionEngine never calls other Engines
- **Domain Consistency, Not Business Consistency**: ProjectionEngine ensures domain invariants, Service ensures business consistency
- **Algorithm Isolation**: Domain algorithms are isolated within ProjectionEngine

### 1.2 ProjectionEngine Position in Architecture

```
Repository
  ↓ Retrieve Domain Objects
SearchEngine
  ↓ Discover Candidates
ProjectionEngine
  ↓ Produce Domain Projections
QueryService
  ↓ Assemble Business Results
```

ProjectionEngine operates:

- **AFTER** Retrieval
- **AFTER** Candidate Discovery
- **BEFORE** Business Assembly

ProjectionEngine transforms already retrieved Domain Objects into deterministic, domain-consistent Projections.

Projection changes representation.
Projection never changes domain semantics.

### 1.3 ProjectionEngine is NOT

ProjectionEngine is NOT:

- Retrieval
- Repository
- Search
- Context Builder
- Workflow
- Service
- DTO Mapper
- Presentation Layer
- Prompt Builder
- Persistence Layer
- LLM Integration

### 1.4 Relationship with Other Engines

ProjectionEngine, EntityEngine, MemoryEngine, RelationshipEngine, ReflectionEngine, and SearchEngine are sibling Domain Engines under the same architectural layer:

- **ProjectionEngine** owns Projection semantics, deterministic projection production, and structure normalization
- **EntityEngine** owns Entity identity, canonical semantics, and evolution
- **MemoryEngine** owns Memory semantic consistency, evidence integrity, and lifecycle
- **RelationshipEngine** owns Relationship semantics, validity, and consistency
- **ReflectionEngine** owns Reflection semantics, candidate evaluation, and knowledge evolution
- **SearchEngine** owns Discovery semantics, candidate validation, and ranking policy

ProjectionEngine operates on retrieved Domain Objects. It never calls other Engines. Service coordinates between Engines.

## 2. Responsibilities

### 2.1 Produce Domain Projections

ProjectionEngine produces domain-consistent projections:

- Transform retrieved Domain Objects into Projections
- Apply projection policies to determine output structure
- Ensure Projections preserve domain meaning
- Maintain deterministic behavior

### 2.2 Enforce Projection Semantics

ProjectionEngine enforces projection semantics:

- Projections must preserve original domain meaning
- Projections must not infer new knowledge
- Projections must follow explicit policies
- Projections must be aggregate-safe

### 2.3 Normalize Projection Structure

ProjectionEngine normalizes projection structures:

- Ensure consistent projection format
- Apply projection type rules
- Maintain structural integrity
- Support multiple projection types

### 2.4 Apply Projection Policies

ProjectionEngine applies projection policies:

- Policy determines what information is included
- Policy determines exclusion rules
- Policy ensures minimal exposure
- Policy maintains domain intent preservation

### 2.5 Preserve Domain Integrity

ProjectionEngine preserves domain integrity:

- Domain identity maintained through projection
- Aggregate boundaries respected
- No domain knowledge created
- No domain state modified

### 2.6 Produce Deterministic Results

ProjectionEngine guarantees deterministic behavior:

- Same input + same policy = same projection
- No randomness in projection output
- Reproducible results guaranteed
- Policy-driven determinism

### 2.7 Remain Independent of Presentation

ProjectionEngine remains presentation-independent:

- Projections are domain objects, not UI elements
- No rendering logic in ProjectionEngine
- No presentation framework dependency
- Technology-agnostic projection production

### 2.8 Explicitly NOT Owned

ProjectionEngine does NOT own:

- **Retrieval** — Repository handles data retrieval
- **Candidate discovery** — SearchEngine handles discovery
- **Context construction** — ContextBuilder handles context (D5)
- **Workflow orchestration** — Service orchestrates multi-step workflows
- **Transaction management** — Service owns transaction boundaries
- **Repository coordination** — Repository owns data access
- **DTO mapping** — Service handles presentation mapping
- **Result assembly** — Service assembles final business results
- **Persistence** — Repository handles database operations
- **Rendering** — Not a domain responsibility
- **Prompt construction** — Not a domain responsibility
- **LLM invocation** — Service manages AI provider communication
- **Entity identity** — EntityEngine owns Entity identity
- **Memory semantics** — MemoryEngine owns Memory consistency
- **Relationship semantics** — RelationshipEngine owns Relationship consistency
- **Reflection semantics** — ReflectionEngine owns Reflection consistency
- **Search/discovery** — SearchEngine owns Discovery domain
- **Cross-Engine coordination** — Service coordinates between Engines

## 3. Public Contract Principles

ProjectionEngine's public contract follows these principles:

### 3.1 Capability-Oriented

Methods are organized by domain capability, not by CRUD operations.

### 3.2 Stateless

ProjectionEngine has no mutable instance state. All state comes from Repository reads.

### 3.3 Deterministic

Given the same input Domain Objects and policy, ProjectionEngine always produces the same Projection.

### 3.4 Domain-Oriented

Returns domain-level results (DomainResult, DomainError), not protocol-specific types.

### 3.5 Side-Effect Free

ProjectionEngine does not directly modify Repository data. It returns domain commands that Service executes.

### 3.6 Explicit Result

Every method returns an explicit result indicating success, failure, or required action.

### 3.7 Repository Agnostic

ProjectionEngine operates on Domain Models, not database schemas.

### 3.8 Workflow Independent

ProjectionEngine makes domain decisions only. It does not orchestrate workflows.

### 3.9 Engine Independent

ProjectionEngine never calls other Engines. All Engine coordination happens at Service layer.

### 3.10 Projection ≠ Creation

ProjectionEngine projects existing domain information.
ProjectionEngine never creates new domain knowledge.

Projection changes representation.
Projection never changes domain semantics.

## 4. Domain Rules

### 4.1 Projection Preservation Rules

#### 4.1.1 Domain Meaning Preservation

> Projection must preserve domain meaning.

- Projections cannot alter original domain semantics
- Meaning must be intact after projection
- Semantic distortion results in rejection

#### 4.1.2 Read-Only Guarantee

> Projection must be read-only.

- Projections do not modify source Domain Objects
- Source objects remain unchanged
- Projection is a transformation, not a mutation

#### 4.1.3 Explicit Policy Requirement

> Projection must follow explicit policies.

- No implicit projection behavior permitted
- Every projection must reference a defined policy
- Missing policy results in rejection

#### 4.1.4 No Knowledge Inference

> Projection must not infer new knowledge.

- Projections cannot add information not present in source
- Inference is forbidden in projection layer
- Only representation changes allowed

### 4.2 Aggregate Safety Rules

#### 4.2.1 Aggregate Boundary Preservation

> Projection must be aggregate-safe.

- Aggregate boundaries respected during projection
- No cross-aggregate contamination
- Aggregate integrity maintained

#### 4.2.2 Minimal Exposure

> Projection must expose only necessary information.

- Complete enough to preserve domain intent
- Minimal enough to avoid exposing unrelated information
- Balance between completeness and minimality

### 4.3 Determinism Rules

#### 4.3.1 Deterministic Output

> Projection must be deterministic.

- Same input always produces same output
- No randomness or non-deterministic behavior
- Policy-driven consistency enforced

#### 4.3.2 Policy Consistency

> Same Input + Same Policy = Same Projection.

- Input determinism guaranteed
- Policy determinism guaranteed
- Combined determinism enforced

### 4.4 Independence Rules

#### 4.4.1 Presentation Independence

> Projection must be independent of presentation.

- No UI/framework dependency
- No rendering logic
- Domain-only concerns

#### 4.4.2 Retrieval Independence

> Projection must be retrieval-agnostic.

- Does not know how data was retrieved
- Independent of search technology
- Independent of repository implementation

### 4.5 Completeness Principle

> Projection must be complete enough to preserve domain intent, but minimal enough to avoid exposing unrelated domain information.

- Completeness ensures semantic integrity
- Minimality ensures security and clarity
- Balance achieved through policy configuration

## 5. Domain Invariants

### 5.1 Projection Never Changes Domain Objects

> ProjectionEngine transforms Domain Objects into Projections without modifying originals.

Source Domain Objects remain immutable through projection operations.

### 5.2 Projection Never Creates Domain Knowledge

> ProjectionEngine never creates new domain knowledge.

Projections only reorganize existing information. No inference or generation permitted.

### 5.3 Projection Preserves Domain Identity

> Domain identity preserved through projection.

EntityIDs, MemoryIDs, and other identifiers remain intact and unmodified.

### 5.4 Same Input + Same Policy = Same Projection

> Deterministic behavior guaranteed.

Identical inputs with identical policies always produce identical projections.

### 5.5 Projection Never Breaks Aggregate Boundaries

> Aggregate boundaries always respected.

No projection crosses aggregate boundaries. Aggregate integrity maintained.

### 5.6 Projection Is Presentation Independent

> Projections are domain objects, not presentation artifacts.

No rendering, UI, or framework dependency exists in ProjectionEngine.

### 5.7 Projection Is Retrieval Independent

> ProjectionEngine does not depend on how data was retrieved.

Independent of search technology, repository implementation, or query syntax.

### 5.8 Projection Contains No Business Workflow

> ProjectionEngine performs no workflow orchestration.

Pure transformation engine. No multi-step operations.

### 5.9 Projection Is Ephemeral and Never Becomes Persisted Domain State

> Projections exist only in memory during service execution.

Projections are never persisted. They are transient representations, not domain entities.

### 5.10 Invariant Hierarchy

```
Domain Consistency
    │
    ├── Projection ≠ Creation
    │       │
    │       ├── Never Changes Domain Objects
    │       └── Never Creates Domain Knowledge
    │
    ├── Determinism
    │       │
    │       ├── Same Input + Same Policy = Same Projection
    │       └── No Randomness
    │
    └── Independence
            ├── Presentation Independent
            ├── Retrieval Independent
            ├── No Business Workflow
            └── Ephemeral (Not Persisted)
```

All invariants are:

- **Universal**: Apply to all Projection operations
- **Context Independent**: Not dependent on specific domain scenarios
- **Always Enforced**: No bypass mechanism exists

### 5.11 Invariant Extension Principle

> New invariants may be introduced in future versions only through architectural evolution while preserving backward compatibility, unless revised by ADR.

Any new invariant must:

- Not violate existing invariants
- Be justified by domain necessity
- Pass D4 principle consistency review
- Be documented with ADR if it changes existing behavior

## 6. Internal Composition

### 6.1 Architecture Overview

```
ProjectionEngine (Public Facade)
│
├── ProjectionValidator Capability     — Projection eligibility validation
├── ProjectionPolicyResolver Capability — Policy selection and resolution
├── ProjectionBuilder Capability        — Projection object construction
└── ProjectionVerifier Capability       — Projection consistency verification
```

ProjectionEngine is a **Facade**. Its internal composition is private. Service depends only on the public contract.

**Important**: Builder is the only component allowed to construct Projection objects.

### 6.2 Capabilities

#### ProjectionValidator Capability

- Validates projection eligibility
- Checks source Domain Object validity
- Verifies policy applicability
- Ensures projection constraints satisfied

#### ProjectionPolicyResolver Capability

- Resolves applicable projection policies
- Selects correct policy for context
- Applies policy rules
- Determines projection scope

#### ProjectionBuilder Capability

- Constructs Projection objects
- Transforms Domain Objects to Projections
- Applies policy-driven transformations
- Builds deterministic output

**Note**: ProjectionBuilder is the ONLY component allowed to construct Projection objects. This ensures consistency and control over projection creation.

#### ProjectionVerifier Capability

- Verifies projection consistency
- Validates domain meaning preservation
- Checks aggregate boundary compliance
- Ensures deterministic correctness

### 6.3 Composition Principles

| Principle | Description |
|-----------|-------------|
| **Composition Over Inheritance** | Internal capabilities use composition. Inheritance prohibited. |
| **Single Responsibility** | Each capability owns exactly one domain concern. |
| **Internal Collaboration Only** | Capabilities collaborate internally. Service never sees them. |
| **Replaceable Internal Capabilities** | Capabilities can be replaced without changing public contract. |
| **Stable Public Facade** | Public contract is the only dependency point for Service. |
| **Builder Monopoly** | Only ProjectionBuilder can construct Projection objects. |

### 6.4 Internal Classification

| Internal Term | Category | Owner |
|---------------|----------|-------|
| ProjectionValidator Capability | B — Engine Component | ProjectionEngine |
| ProjectionPolicyResolver Capability | B — Engine Component | ProjectionEngine |
| ProjectionBuilder Capability | B — Engine Component | ProjectionEngine |
| ProjectionVerifier Capability | B — Engine Component | ProjectionEngine |
| Projection Policy | C — Engine Policy | ProjectionEngine |
| Projection Type Policy | C — Engine Policy | ProjectionEngine |

## 7. Extension Points

### 7.1 Allowed Extensions

The following are architecturally open for extension:

| Extension Type | Category | Description |
|----------------|----------|-------------|
| **New Projection Policy** | C | Add new projection policies |
| **New Projection Type** | C | Add new projection types |
| **New Projection Rule** | C | Add new projection rules |
| **New Verification Rule** | C | Add new verification rules |

### 7.2 Architecturally Closed

The following are closed and require ADR to change:

| Closed Aspect | Reason |
|---------------|--------|
| **Domain Scope** | Projection domain is fixed by architecture |
| **Layer Responsibility** | Engine layer cannot own workflow or persistence |
| **Engine Dependency Model** | Engine calls Repository only, never other Engines |
| **Public Contract Stability** | Contract changes require ADR |
| **Domain Invariants** | Existing invariants cannot be weakened |
| **Presentation Independence** | Cannot introduce presentation logic |
| **Retrieval Independence** | Cannot introduce retrieval logic |

### 7.3 Extension Principles

| Principle | Description |
|-----------|-------------|
| **Open for Domain Evolution** | New domain rules and capabilities can be added |
| **Closed for Architectural Responsibility** | Layer boundaries cannot be crossed |
| **Stable Public Contract** | Extensions must not break existing contract |
| **No New Engine Without Independent Capability** | No new Engine unless a completely independent Domain Capability emerges |
| **Projection-Tech Agnostic** | Extension Points may introduce new projection semantics, but must not introduce new architectural responsibilities |

### 7.4 Extension Constraints

Extensions must NOT introduce:

- Workflow orchestration
- Retrieval logic
- Persistence logic
- Presentation logic
- DTO mapping
- Prompt construction
- LLM integration

ProjectionEngine must remain projection-technology agnostic.

### 8.1 Testing Principles

| Principle | Description |
|-----------|-------------|

| **Rule-Driven Testing** | Tests verify domain rules are enforced |
| **Invariant Protection** | Tests ensure invariants are never violated |
| **Stateless Verification** | Same input always produces same result |
| **Boundary Testing** | Tests verify Engine-Repository boundary |
| **Extension Compatibility** | New capabilities must not break existing tests |

### 8.2 Testing Layers

#### Public Contract Tests

- Project Domain Objects
- Validate Projection Eligibility
- Apply Projection Policy
- Produce Deterministic Projection
- Reject Invalid Projection Requests

#### Domain Rule Tests

- Domain Meaning Preservation
- Read-Only Guarantee
- Explicit Policy Requirement
- No Knowledge Inference
- Aggregate Safety
- Determinism
- Presentation Independence
- Retrieval Independence

#### Domain Invariant Tests

- Projection Never Changes Domain Objects
- Projection Never Creates Domain Knowledge
- Projection Preserves Domain Identity
- Same Input + Same Policy = Same Projection
- Projection Never Breaks Aggregate Boundaries
- Projection Is Presentation Independent
- Projection Is Retrieval Independent
- Projection Contains No Business Workflow
- Projection Is Ephemeral and Never Becomes Persisted Domain State

#### Internal Component Tests

- ProjectionValidator Capability
- ProjectionPolicyResolver Capability
- ProjectionBuilder Capability (construction monopoly)
- ProjectionVerifier Capability

#### Projection Policy Compatibility Tests

- New Policy passes all invariant tests
- Policy does not violate existing invariants
- Policy compatible with all capabilities

#### Regression Tests

- Existing domain rules continue to work
- No invariant violations from new code
- Extension compatibility verified

### 8.3 Test Dependencies

```
ProjectionEngine Test
├── ProjectionEngine (SUT)
├── Repository Mock (returns Domain Models)
├── Domain Result Assertion
└── Domain Error Assertion
```

- Tests mock Repository — do not use real database
- Tests verify Engine in isolation — no other Engines involved
- Tests do not involve Service layer — Engine tested directly

### 8.4 Excluded Tests

The following are explicitly excluded from ProjectionEngine tests:

- **Repository Tests** — Repository tested separately
- **Workflow Tests** — Workflow tested at Service layer
- **Service Tests** — Service tested separately
- **DTO Tests** — DTO mapping outside ProjectionEngine scope
- **API Tests** — API layer tested at Entry Layer (D5)
- **Prompt Tests** — Prompt construction outside ProjectionEngine scope

### 8.5 Policy Compatibility Requirement

> Every new Projection Policy must automatically pass the complete Projection consistency test suite before becoming a supported policy.

This requirement ensures:

- No unsupported policy introduces invariant violations
- All policies validated before deployment
- Consistency maintained across policy additions

### 8.6 Verification Requirements

Tests must verify:

- **Domain consistency** — Projection domain rules enforced
- **Frozen rules** — All nine invariants maintained
- **No Repository dependency** — Tests do not depend on persistence
- **No Service dependency** — Engine tested independently
- **No Engine dependency** — No cross-Engine calls in tests
