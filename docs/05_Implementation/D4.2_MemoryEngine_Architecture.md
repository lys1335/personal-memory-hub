## 1. Purpose

### 1.1 Core Identity

MemoryEngine is the **Memory Domain semantic consistency owner**.

It owns:

- Memory semantic evolution
- Evidence integrity enforcement
- Memory lifecycle domain rules
- Memory state evaluation

MemoryEngine is a **Domain Engine**, not a persistence wrapper. It does not call databases directly. It operates on Domain Models provided by Repository.

This document adheres to D4 principles:
- **One Domain Capability → One Engine**: MemoryEngine owns Memory domain only
- **Engine is a Stable Facade**: Public contract is stable, internal composition is private
- **Domain Result, Not Protocol Result**: Returns domain-level results
- **No Cross-Engine Calls**: MemoryEngine never calls other Engines
- **Domain Consistency, Not Business Consistency**: MemoryEngine ensures domain invariants, Service ensures business consistency
- **Algorithm Isolation**: Domain algorithms are isolated within MemoryEngine

### 1.2 Explicitly NOT Owned

MemoryEngine does NOT own:

- **Workflow** — MemoryService orchestrates multi-step workflows
- **Repository access** — Repository owns data access
- **Transaction** — Service owns transaction boundaries
- **Search** — SearchEngine owns retrieval algorithms
- **Projection** — ProjectionEngine owns view assembly
- **Cross-Engine coordination** — Service coordinates between Engines

## 2. Responsibilities

### 2.1 Memory Domain Validation

MemoryEngine validates that each Memory satisfies domain invariants before acceptance:

- Every Memory has associated Evidence
- Memory semantic content is coherent
- Memory hierarchy level (L0-L4) assignment is valid
- Memory state transitions are legal

### 2.2 Memory Lifecycle Management

MemoryEngine manages the domain-level lifecycle of Memories:

- **Creation** — Validates and assigns initial state
- **Evolution** — Applies progressive semantic refinement
- **Consolidation** — Evaluates merge eligibility
- **Archive Eligibility** — Determines archive candidacy
- **Evaluation** — Computes importance, confidence, freshness

### 2.3 Evidence Consistency Enforcement

MemoryEngine ensures evidence integrity:

- New Evidence is properly linked to Memory
- Evidence chain is unbroken
- Evidence semantics are preserved during Memory evolution
- Evidence cannot be orphaned by Memory state changes

### 2.4 Memory State Evaluation

MemoryEngine evaluates Memory state for domain purposes:

- Importance scoring (domain rule-based)
- Confidence assessment (evidence density)
- Freshness evaluation (temporal decay)
- Archive candidate identification

### 2.5 Memory Domain Rule Enforcement

MemoryEngine enforces domain rules:

- Progressive evolution (Monotonic refinement)
- Rule-based consolidation (not arbitrary merges)
- Traceability preservation (evidence chain never lost)
- Domain purity (Memory semantics not contaminated by query concerns)

## 3. Public Contract Principles

MemoryEngine's public contract follows these principles:

### 3.1 Capability-Oriented

Methods are organized by domain capability, not by CRUD operations.

### 3.2 Stateless

MemoryEngine has no mutable instance state. All state comes from Repository reads.

### 3.3 Deterministic

Given the same input Memory and Evidence, MemoryEngine always produces the same Domain Result.

### 3.4 Domain-Oriented

Returns domain-level results (DomainResult, DomainError), not protocol-specific types.

### 3.5 Side-Effect Free

MemoryEngine does not directly modify Repository data. It returns domain commands that Service executes.

### 3.6 Explicit Result

Every method returns an explicit result indicating success, failure, or required action.

### 3.7 No Cross-Engine Calls

MemoryEngine does NOT call other Engines. Service is the only orchestrator. This is a hard architectural constraint inherited from D4 principles.

## 4. Domain Rules

### 4.1 Evidence Requirement

> Every Memory must have associated Evidence. No Evidence, no Memory.

- New Memories are rejected without valid Evidence
- Evidence chain must be unbroken during Memory evolution
- Evidence cannot be removed from an existing Memory

### 4.2 Progressive Evolution

> Memory semantics evolve progressively, never regress.

- Each evolution step refines or consolidates existing semantics
- Previous states are preserved through Evidence chain
- Evolution is monotonic — never reverts to a less refined state

### 4.3 Rule-Based Consolidation

> Memory consolidation follows explicit domain rules, not arbitrary decisions.

- Consolidation criteria are defined in domain rules
- Consolidation preserves all evidence
- Consolidation updates semantic content, not history

### 4.4 Traceability

> Every Memory state change must be traceable to its Evidence origin.

- Evidence chain is never broken
- State transitions are recorded as domain events
- Historical reconstruction is always possible through Evidence

### 4.5 Archive Eligibility

> Archive eligibility is determined by domain rules, not arbitrary thresholds.

- Rules consider: age, confidence decay, semantic redundancy
- Archive does not delete Memory — it marks for archival
- Archived Memories remain queryable through ProjectionEngine

### 4.6 Domain Isolation

> MemoryEngine owns Memory domain semantics only.

- Memory content is not influenced by query needs
- Memory structure is not influenced by presentation needs
- Memory domain rules are independent of Service workflow

### 4.7 Policy-Driven Behavior

> MemoryEngine behavior is driven by configurable policies.

- Policies control evolution speed, consolidation thresholds
- Policies are internal to MemoryEngine (Category C)
- New policies can be added without changing public contract

## 5. Domain Invariants

### 5.1 Every Memory Has Evidence

> No Memory exists without valid, traceable Evidence.

This is the foundational invariant. If violated, Memory creation is rejected.

### 5.2 Semantic Consistency

> Memory semantics remain internally consistent across all state transitions.

Contradictory statements within a Memory are resolved through consolidation rules, not ignored.

### 5.3 Traceability Is Never Lost

> Evidence chain is preserved through all Memory lifecycle transitions.

Even when Memories are consolidated or archived, the evidence origin remains traceable.

### 5.4 Evolution Is Monotonic

> Memory semantic refinement never regresses.

Each evolution step produces equal or greater semantic clarity. Never less.

### 5.5 Domain Purity

> Memory domain rules are not contaminated by query or projection concerns.

MemoryEngine does not optimize for query performance or presentation format.

### 5.6 Policy Compliance

> MemoryEngine always complies with configured domain policies.

Policy changes take effect immediately for future operations. Existing Memories are not retroactively modified.

### 5.7 Invariant Extension Principle

> New invariants may be introduced in future versions only through architectural evolution while preserving backward compatibility, unless revised by ADR.

Any new invariant must:

- Not violate existing invariants
- Be justified by domain necessity
- Pass D4 principle consistency review
- Be documented with ADR if it changes existing behavior

## 6. Internal Composition

### 6.1 Architecture Overview

```
MemoryEngine (Public Facade)
│
├── Validation Capability    — Domain rule validation
├── Lifecycle Capability     — State transition management
├── Policy Capability        — Configurable policy enforcement
├── Evaluation Capability    — State evaluation algorithms
└── Evidence Capability      — Evidence chain management
```

MemoryEngine is a **Facade**. Its internal composition is private. Service depends only on the public contract.

### 6.2 Capabilities

#### Validation Capability

- Enforces Evidence Requirement invariant
- Validates Memory semantic coherence
- Checks state transition legality
- Rejects invalid Memories at domain level

#### Lifecycle Capability

- Manages Memory state transitions
- Applies progressive evolution rules
- Handles consolidation workflows
- Manages archive eligibility evaluation

#### Policy Capability

- Loads and applies domain policies
- Evaluates policy conditions
- Enforces policy-driven behavior
- Supports policy hot-reload (no restart)

#### Evaluation Capability

- Computes importance scores
- Assesses confidence levels
- Evaluates temporal freshness
- Identifies consolidation candidates

#### Evidence Capability

- Maintains evidence chain integrity
- Links new Evidence to existing Memories
- Validates evidence completeness
- Preserves evidence during evolution

### 6.3 Composition Principles

| Principle | Description |
|-----------|-------------|
| **Composition Over Inheritance** | Internal capabilities use composition. Inheritance prohibited. |
| **Single Responsibility** | Each capability owns exactly one domain concern. |
| **Internal Collaboration Only** | Capabilities collaborate internally. Service never sees them. |
| **Replaceable Internal Capabilities** | Capabilities can be replaced without changing public contract. |
| **Stable Public Facade** | Public contract is the only dependency point for Service. |

### 6.4 Internal Classification

| Internal Term | Category | Owner |
|---------------|----------|-------|
| Validation Capability | B — Engine Component | MemoryEngine |
| Lifecycle Capability | B — Engine Component | MemoryEngine |
| Policy Capability | B — Engine Component | MemoryEngine |

| Evidence Capability | B — Engine Component | MemoryEngine |
| Archive Policy | C — Engine Policy | MemoryEngine |
| Evolution Policy | C — Engine Policy | MemoryEngine |
| Consolidation Policy | C — Engine Policy | MemoryEngine |

## 7. Extension Points

### 7.1 Allowed Extensions

The following are architecturally open for extension:

| Extension Type | Category | Description |
|----------------|----------|-------------|
| **Policy** | C | New domain policies (e.g., retention policy) |
| **Lifecycle Strategy** | D | New lifecycle transition strategies |
| **Validation Rules** | C | New domain validation rules |
| **Domain Algorithms** | C | New evaluation algorithms |
| **Internal Capability Composition** | B | Refactor internal capabilities |

### 7.2 Architecturally Closed

The following are closed and require ADR to change:

| Closed Aspect | Reason |
|---------------|--------|
| **Domain Scope** | Memory domain is fixed by architecture |
| **Layer Responsibility** | Engine layer cannot own workflow or persistence |
| **Engine Dependency Model** | Engine calls Repository only, never other Engines |
| **Public Contract Stability** | Contract changes require ADR |
| **Domain Invariants** | Existing invariants cannot be weakened |

### 7.3 Extension Principles

| Principle | Description |
|-----------|-------------|
| **Open for Domain Evolution** | New domain rules and policies can be added |
| **Closed for Architectural Responsibility** | Layer boundaries cannot be crossed |
| **Stable Public Contract** | Extensions must not break existing contract |

## 8. Testing Strategy

### 8.1 Testing Principles

| Principle | Description |
|-----------|-------------|
| **Public Contract First** | Tests verify public contract, not internal implementation |
| **Rule-Driven Testing** | Tests verify domain rules are enforced |
| **Invariant Protection** | Tests ensure invariants are never violated |
| **Stateless Verification** | Same input always produces same result |
| **Boundary Testing** | Tests verify Engine-Repository boundary |
| **Extension Compatibility** | New policies/strategies must not break existing tests |

### 8.2 Testing Layers

#### Contract Tests

- Verify public contract is stable
- Verify Stateless property
- Verify Deterministic property
- Verify Domain Result (not protocol Result)

#### Rule Tests

- Evidence Requirement enforcement
- Progressive Evolution enforcement
- Rule-Based Consolidation enforcement
- Traceability preservation
- Archive Eligibility rules
- Domain Isolation enforcement
- Policy-Driven behavior

#### Invariant Tests

- Every Memory Has Evidence
- Semantic Consistency
- Traceability Is Never Lost
- Evolution Is Monotonic
- Domain Purity
- Policy Compliance

#### Regression Tests

- Existing domain rules continue to work
- No invariant violations from new code
- Extension compatibility verified

### 8.3 Test Dependencies

```
MemoryEngine Test
├── MemoryEngine (SUT)
├── Repository Mock (returns Domain Models)
├── Domain Result Assertion
└── Domain Error Assertion
```

- Tests mock Repository — do not use real database
- Tests verify Engine in isolation — no other Engines involved
- Tests do not involve Service layer — Engine tested directly

## 9. Future Evolution Notes

### 9.1 Expected Evolution Paths

The following evolution paths are architecturally open:

- **Additional Policies** — New domain policies (e.g., retention, compliance)
- **Additional Validation Rules** — New domain validation rules
- **Additional Lifecycle Strategies** — New state transition strategies
- **Additional Domain Algorithms** — New evaluation algorithms
- **Internal Capability Refactoring** — Restructure internal composition

### 9.2 Evolution Constraints

All future evolution shall preserve:

- **Public Contract** — No breaking changes without ADR
- **Domain Scope** — MemoryEngine owns Memory domain only
- **Domain Invariants** — Existing invariants cannot be weakened
- **Layer Responsibility** — Engine cannot own workflow or persistence
- **Engine Dependency Model** — Engine calls Repository only

### 9.3 Evolution Process

When evolving MemoryEngine:

1. Verify change does not violate frozen D4 principles
2. Classify change using Engine Classification Categories (A-E)
3. If public contract changes, create ADR
4. If domain invariant changes, create ADR
5. Update this document to reflect new capabilities/policies
6. Add corresponding tests

### 9.4 Closed Evolution Paths

The following are architecturally closed:

- MemoryEngine calling other Engines
- MemoryEngine owning workflow or transaction
- MemoryEngine directly accessing database
- MemoryEngine owning search or projection logic
- MemoryEngine breaking any documented invariant

Any proposal to change these requires ADR.
